01

The northstar in one line

A codex-first new user reaches a remotely-controllable, end-to-end-encrypted session with a single install and a single command.

install Only the codex fork
run /remote on
self-onboard GitHub device flow in the codex TUI
daemon up Per-machine daemon + embedded happy-server
expose Private Microsoft Dev Tunnel
result Discoverable & controllable in the Happy app — E2EE
🚫🗄️
No central server

No broker, relay, or pub-sub. Nothing transits a Happy broker, the phone, or the mobile app — the only channel is Microsoft Dev Tunnels.

📦🖥️
Embedded server = the session plane

The per-daemon happy-server is load-bearing (pair · /v3 · Socket.IO). The 3-lens verdict (906ed67b): it cannot be dropped.

🔌🌐
Dev Tunnels are the sole path

Discovery, rendezvous, signaling, data, and auth all ride Microsoft Dev Tunnels — operator machines are enumerated with devtunnel list --json. The exact Happy-client rendezvous for a fresh codex-onboarded machine is still OPEN.

🔐
End-to-end encrypted

Message bodies + agent state are ciphertext on the wire; only session metadata is plaintext. Trust = operator tunnel ownership + TOFU pinning + sealing.

04

Today vs the northstar

The autoconnect overlay already ships and works — but today it leans on happy-cli for the daemon, the tunnel, and onboarding. The northstar removes that friction.

Today

Works, but happy-cli-gated

  • Install happy-cli (Node) separately from codex.
  • Onboard via happy-cli (happy / happy codex) — not codex.
  • Run the happy-cli daemon: it writes ~/.happy/machine.json, binds the 127.0.0.1 listeners, and hosts the Dev Tunnel.
  • Only then does raw codex autoconnect (remote_session) connect to the per-daemon happy-server at 127.0.0.1:<tunnelPort>.
✅ Already correct today: the codex-happy overlay connects to the local per-daemon happy-server — never an external one. The architecture is right; only the setup friction is the gap.
Northstar

Codex-first, self-contained

  • Install only the codex fork. No separate happy-cli step.
  • Codex self-onboards: GitHub device flow shown right in the TUI, mints its own ~/.happy creds (access.key hardened to 0o600 — the M1 fix this work carries).
  • The per-machine daemon (embedded happy-server) comes up frictionlessly — OPEN codex-native or auto-managed happy-cli.
  • Session is discoverable + controllable in the Happy app over Dev Tunnels. Subsequent runs just connect.
🎯 Same architecture, zero setup tax: one install, one /remote on, and the phone/web/local Happy clients see the session — still no central server.
05

Open decisions for the operator

These are deliberately not decided in this doc. The parallel brainstorm (codex-autoconnect-self-contained-zero-friction) will recommend; the operator decides.

D1 · central Who owns the per-machine daemon?

Both keep the load-bearing embedded happy-server (the session plane) — they differ only in who starts and ships it. Toggle the architecture diagram above to see each one drawn.

Option A · codex-native daemon

Codex itself bundles & starts the embedded happy-server.
Pros
  • True "install only codex" — nothing else on the machine.
  • Fewer moving parts to install, version, and ship.
  • No Node runtime dependency for the daemon.
Cons
  • Must port / embed the happy-server (and tunnel mgmt) into the fork — larger surface.
  • Re-implements daemon lifecycle codex doesn't own today.
  • Higher upstream-conflict / maintenance cost in the fork.

Option B · happy-cli daemon, made frictionless

Codex auto-installs & auto-starts the existing happy-cli daemon on demand.
Pros
  • Reuses the proven happy-cli daemon, tunnel mgmt & machine.json contract.
  • Much smaller fork change — codex just orchestrates an existing component.
  • happy-cli keeps evolving the daemon independently.
Cons
  • A Node/happy-cli install still exists — just hidden behind auto-install.
  • Codex must manage another process's lifecycle & failures.
  • Not literally "only codex on disk."

D2 · discovery How does a Happy client find this machine's tunnel?

Reuse the Scope-A devtunnel list --json discovery + Dev-Tunnel rendezvous as-is, or add an explicit pairing/registration step so the app can locate the machine? The rendezvous mechanism for a fresh, codex-onboarded machine is not yet pinned. OPEN — pending the brainstorm.
