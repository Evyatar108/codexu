## 2. Recommendation: **Option A (inline the hoist)** — with stronger reasoning than the brief suggests

Take the cheapest path. Three concurrent pieces of evidence make A the clearly correct call:

1. **The plugin treats AST-only literal data as a security boundary, not a parser limitation** (parser commit `74e45f2c` body; `validate-data.test.ts:80-87`). Extending the parser to walk a const symbol table doesn't break that invariant *today* — but it widens the surface area of the trusted parser and creates a slippery-slope to "well, why not function calls if they're pure?" The team has already paid review cost to lock the invariant down (CLAUDE.md #10).
2. **There is no ecosystem pressure for Option B.** Filesystem search confirms codexu is the only consumer. The shipped template (`templates/overview-data.template.js:13`) demonstrates the literal-only contract is the bookkeeper-facing API. Extending the parser to support a pattern that exactly one consumer wants to use exactly one time is over-engineering.
3. **The "symmetric parser update" cost from H3 was illusory.** With `set-override` removed in v2.0.0, the brief's H3 multi-file fan-out is gone — but so is the corresponding argument that "we have to touch two parsers anyway, so just extend both." Option A's blast radius is now genuinely smaller than Option B's.

Defer Option B until/unless a SECOND consumer appears and credibly demands the hoist pattern. At that point, B becomes a justifiable plugin feature with real demand behind it.

## 4. Things to NOT do

- **Do not implement Option B "just in case" a second consumer appears.** YAGNI plus the documented security-boundary invariant. The team explicitly wrote "AST-only without eval or new Function" in the parser commit (`74e45f2c`). Quietly broadening the contract erodes the auditability of `overview.validate_data`.
- **Do not propose "path C2": `new Function(source + '; return window.OVERVIEW_DATA;')`** in a sandboxed context. The parser commit's own subject line forbids this. The `validate-data.test.ts:80-87` test explicitly exists to prevent it, using `process.exit(1)` as the payload — a sandboxed `new Function` with a stub `window` would still execute that statement. No vm-context flag changes the fact that the security contract is "do not execute". This option is dead on arrival.
- **Do not delete the orphan `test-fixtures/overview-data.rich.js` without first verifying its history.** It was added in commit `2dec5c10` (US-002 upsert-task-edit AST mutator) and may be reachable from a future test suite. Safer to repurpose it as the negative-case fixture for the new regression test.
- **Do not regenerate `plans/overview.html` by hand-editing.** Run `pnpm overview:build` (per `tools/overview-viewer/CLAUDE.md:13`) so the singleFile inline plugin picks up the new data and `esbuild` re-minifies the sidecar against the 500 KB single-file budget (`tools/overview-viewer/CLAUDE.md:77`).
- **Do not collapse the watcher's three chokidar instances or remove depth caps while in the area.** Plugin CLAUDE.md invariant #14 (`D:/ai-developer-toolkit/plugins/ralph-overview/CLAUDE.md:83`) calls this out as a Windows-cold-start correctness contract — unrelated to A/B/C but it's the kind of "while I'm here" cleanup an agent might propose.
- **Do not propose moving `CODEXU_UI` into a per-scope file imported via ES modules.** Already ruled out-of-scope by the brief, but worth re-citing because it's the seductive shortcut: `vite.config.ts` injects the data file via `<script>` and `App.tsx` re-executes it via `new Function(text)()` (architecture invariant #9 at `CLAUDE.md:73`). ESM imports would need a parallel HMR pathway and break the static singleFile build.
