## C2 - The child-process issue and fix

There are two related-but-distinct historical bugs:

1. **The operator's hinted Git Bash `features.unified_exec=false` guard is real, but it is not the distinct process-tree cleanup fix.** Commit `fff065934c281bfd3df825eaadbb768722ac4576` says exactly why the old guard was wrong: "The Cygwin/MSYS2 guard was disabling unified_exec for all bash/sh/zsh shells. The ConPTY crash it guarded against only occurs when tty=true, but exec_command defaults to tty=false (pipe I/O), which is safe on Cygwin. Removing the blanket override allows await_background_completion and D-001 notifications to work on Windows with Git Bash." The diff removes `is_cygwin_shell(shell)` and `flags.push("features.unified_exec=false")` from `provider_config_flags` (`fff065934c:codex-rs/codex-copilot-launcher/src/config.rs:60-79`) and flips the test from expecting the false flag to asserting it is absent (`fff065934c:codex-rs/codex-copilot-launcher/src/config.rs:101-116`). Mechanism: the old code conflated all Git Bash/Cygwin use with ConPTY/TTY use; with unified exec's default `tty=false`, Git Bash uses pipe I/O, so the ConPTY crash path is not exercised. Reintroducing that guard would not orphan child processes, but it would disable unified_exec features such as background completion/notifications for Git Bash users. The invariant is explicit in current docs (`codex/docs/implementation/patch-surface.md:797-801`, `:1760-1764`) and regression history (`codex/docs/implementation/regression-history.md:216-227`).

2. **There is also a separate child/grandchild process bug and fix: `f11c5d8d2b37c33a3ca5c503acaad756ecdbff2e`, `fix(windows): prevent post-completion hang via Job Object-based child-tree cleanup`.** This is the literal child-process fix. Its rationale says that on Windows, pipe handles for a shell child's stdout/stderr are inheritable; when the shell (`bash`, `cmd.exe`) spawns long-running grandchildren (`cargo`, `rustc`, `link.exe`), those grandchildren inherit the pipe write ends; if the immediate shell exits while grandchildren keep running, the pipe write ends stay open, `ReadFile` never sees EOF, `BlockingPool::Drop` waits forever, and `codex-core.exe` hangs indefinitely (`f11c5d8d2b3:codex-rs/core/src/windows_job.rs:1-20`).

The `f11c5d8d2b3` fix is: create a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, spawn the child with `CREATE_SUSPENDED`, assign it to the job before it executes, resume it, and install a background watcher that waits on a duplicated child process handle; when the immediate child exits, the watcher drops the job handle, Windows terminates every descendant still in the job, descendants close inherited pipe handles, and blocked readers can EOF (`f11c5d8d2b3:codex-rs/core/src/windows_job.rs:12-20`, `:96-127`, `:198-216`). The spawn-side hunk is in `spawn_child_async`: it sets `CREATE_SUSPENDED`, spawns with `kill_on_drop(true)`, calls `attach_windows_job(&child)`, and the attach flow creates the job, assigns the child, resumes it, then calls `close_job_on_child_exit(raw_handle, job)` (`f11c5d8d2b3:codex-rs/core/src/spawn.rs:125-189`).

So the answer to "is the child-process issue the `fff065` unified_exec guard?" is: **the recollection likely combines two nearby Windows/Git-Bash fixes.** `fff065` is the Git-Bash-specific unified_exec/ConPTY guard removal. The distinct child-process bug exists too, but its SHA is `f11c5d8d2b37c33a3ca5c503acaad756ecdbff2e`, and it is a Windows tool-exec child-tree cleanup fix rather than a Git-Bash-only default-shell detector fix. It matters for Git Bash because Git Bash makes `bash.exe` the immediate shell that can spawn real grandchildren, but the same bug also applies to `cmd.exe`/other Windows shell children.

## C3 - Current code assessment and fresh-impl requirements

The current code still contains both protections:

- **Git Bash/unified_exec guard stays removed, and Copilot launcher now forces unified_exec on.** Current launcher `provider_config_flags` emits `features.unified_exec=true` unconditionally for Copilot sessions (`codex/codex-rs-overlay/codex-copilot-launcher/src/config.rs:91-95`) and appends `default_shell=<path>` without any Cygwin/MSYS false guard (`codex/codex-rs-overlay/codex-copilot-launcher/src/config.rs:106-108`). The test asserts `features.unified_exec=false` is never emitted for a Git Bash shell (`codex/codex-rs-overlay/codex-copilot-launcher/src/config.rs:147-165`) and another test asserts the true flag is present (`codex/codex-rs-overlay/codex-copilot-launcher/src/config.rs:168-180`). Upstream's `Feature::UnifiedExec` still defaults off on Windows (`codex/external/repos/codex-patched/codex-rs/features/src/lib.rs:755-760`), so this launcher flag remains load-bearing.

- **Session shell selection and command derivation route Git Bash through existing shell args.** `Session::new` currently chooses explicit `user_shell_override`, then zsh-fork, then `shell::default_user_shell()` (`codex/external/repos/codex-patched/codex-rs/core/src/session/session.rs:840-860`). `exec_command` uses the session shell unless the model supplies an explicit shell, then calls `shell.derive_exec_args(...)` (`codex/external/repos/codex-patched/codex-rs/core/src/tools/handlers/unified_exec.rs:98-125`). Bash-family shells produce `[shell_path, -c/-lc, command]` (`codex/external/repos/codex-patched/codex-rs/core/src/shell.rs:41-52`). This means a fresh `Feature::WindowsGitBashShell` branch at the session seam can reuse the current unified_exec/process path if it returns a normal `ShellType::Bash` with the Git Bash path.

- **Current process spawning still goes through the Job Object seam.** Legacy exec calls `spawn_child_async(SpawnChildRequest { ... stdio_policy: RedirectForShellTool, ... })` (`codex/external/repos/codex-patched/codex-rs/core/src/exec.rs:945-958`), and that seam pipes stdout/stderr, sets Windows `CREATE_SUSPENDED`, spawns with `kill_on_drop(true)`, and attaches the Windows job wrapper (`codex/external/repos/codex-patched/codex-rs/core/src/spawn.rs:107-145`, `:176-195`). The current `windows_job.rs` rationale and implementation still match the original fix: kill-on-close Job Object (`codex/external/repos/codex-patched/codex-rs/core/src/windows_job.rs:1-20`, `:95-127`), assign/resume (`codex/external/repos/codex-patched/codex-rs/core/src/spawn.rs:176-187`), and close the job from a watcher that waits on a duplicated process handle (`codex/external/repos/codex-patched/codex-rs/core/src/windows_job.rs:197-227`). Unified exec stores live processes and terminates via `UnifiedExecProcess::terminate()` (`codex/external/repos/codex-patched/codex-rs/core/src/unified_exec/process.rs:204-220`), while background process lifecycle is monitored by `spawn_exit_watcher` (`codex/external/repos/codex-patched/codex-rs/core/src/unified_exec/async_watcher.rs:114-192`) and stored from `UnifiedExecProcessManager::store_process` (`codex/external/repos/codex-patched/codex-rs/core/src/unified_exec/process_manager.rs:814-865`).

- **Legacy exec also has timeout fallback for inherited pipe hangs.** The non-unified path documents the same grandchild-pipe risk (`codex/external/repos/codex-patched/codex-rs/core/src/exec.rs:74-81`), kills process groups/immediate child on timeout or Ctrl-C (`codex/external/repos/codex-patched/codex-rs/core/src/exec.rs:1360-1375`), and aborts output-reader tasks after an I/O drain timeout (`codex/external/repos/codex-patched/codex-rs/core/src/exec.rs:1381-1395`). But for Git Bash sessions, the intended path is still unified_exec with the Job Object seam preserved, not fallback to legacy shell-command behavior.

**Conclusion for the fresh implementation:** the current core already contains the child-tree cleanup fix; the fresh `Feature::WindowsGitBashShell` implementation does **not** need to re-implement Job Objects. It must, however, explicitly preserve these items so neither historical bug is reintroduced:

1. **Do not add any Git-Bash/Cygwin/MSYS branch that forces `features.unified_exec=false`.** The fresh feature should select the session shell only; it should not change the `Feature::UnifiedExec` state. Git Bash with default `tty=false` pipe I/O is the safe path established by `fff065934c` and current invariants (`codex/docs/implementation/patch-surface.md:797-801`, `:1760-1764`).
2. **Keep Copilot sessions forcing `features.unified_exec=true` unless the implementation deliberately replaces that policy with an equivalent.** Because `Feature::UnifiedExec` is still Windows-default-off (`features/src/lib.rs:755-760`), selecting Git Bash as the default shell without unified_exec would lose background notifications/completion behavior and revive the `fff065` regression class.
3. **Route Git Bash commands through the existing `exec_command`/unified_exec/session-shell path, not through a new direct `tokio::process::Command::spawn` call.** The Job Object cleanup is attached in the shared spawn path (`spawn_child_async` and `windows_job.rs`). A fresh helper should only detect Git Bash and return a `ShellType::Bash`; it should not create a parallel process-spawning path that bypasses `spawn_child_async`/JobObject invariants.
4. **Preserve the Git-for-Windows-first detector ordering.** Use the `1d828e5947` detector shape (hard-coded Git-for-Windows paths, `%LOCALAPPDATA%`, `where git` to sibling `bin\bash.exe`/`usr\bin\bash.exe`, then last-resort `where bash`) rather than generic `which("bash")`, so the feature does not accidentally select WSL `bash.exe` first (`1d828e5947:codex-rs/codex-copilot-launcher/src/setup.rs:182-210`, `:216-245`).
5. **Add/keep an invariant that Windows tool-exec children keep the Job Object wrapper.** Current patch-surface invariants 12 and 13 cover `spawn_child_async` -> `attach_windows_job` and assign-before-resume ordering (`codex/docs/implementation/patch-surface.md:790-791`). The fresh Git Bash plan should mention those are must-preserve but should not need to alter them.
