# Brainstorm synthesis — LAN-based, known-devices-only remote-session transport (additive to Dev Tunnels)

**Idea:** ADD a LAN-based, known-devices-only remote-session connectivity transport ALONGSIDE Microsoft Dev Tunnels (Dev Tunnels stays the default; LAN is opt-in/selectable). Motivation: the operator's corporate/org policy blocks Dev Tunnels, so the remote-session feature is currently unusable. Primary target device: Android e-ink tablet (BOOX).

## The one load-bearing finding all three lenses converged on
The Microsoft Dev Tunnels gateway is doing **two jobs at once**: (a) **reachability** (a private URL the tablet can reach across NAT) and (b) **authentication** (only the operator's blessed devices can even reach the session plane). The embedded happy-server's **tunnel listener has ZERO per-request auth** — it "collapses identity to `tofuConfig.localUserId`" and trusts that anything reaching the socket already passed the gateway (`packages/happy-server/sources/app/api/api.ts:104-117`; `index.ts:101-108` `assertOperatorIdentityGate` THROWS on any non-loopback bind unless `auth === 'loopback'`). A LAN transport gets (a) reachability for free but **DELETES (b)**. Codex verified the concrete bypass: `/pair/complete` (`packages/happy-server/sources/app/api/routes/pairRoutes.ts:59-119`) is unauthenticated, so **any host on the LAN that can reach a naive 0.0.0.0 bind can self-enroll as a paired device.** E2E session encryption protects message *content* but does NOT gate route *access*.

**Unanimous verdict:** an IP allowlist, host allowlist, or mDNS-name trust **alone is NO-GO** (spoofable; bypassable on a hostile corporate LAN). The "known devices" boundary MUST be a **server-side, per-request, cryptographic, fail-closed** auth gate at the listener, enforced BEFORE any non-loopback bind is permitted — and it must cover `/pair/complete`, all tunnel-only HTTP routes, AND the Socket.IO handshake. This also directly contradicts the fork's own written invariant (`packages/happy-cli/AGENTS.md` "Codex Transport Security Model": the embedded server must "never [be exposed] on 0.0.0.0, LAN addresses, public addresses, or tunnels"), so relaxing it needs an explicit, reviewed amendment.

## Existing seams that make this additive/selectable (verified)
- **Pluggable transport provider:** `DaemonTunnelProvider` interface (`packages/happy-cli/src/tunnel/provider.ts:14-18`), implemented by `DevTunnelsDaemonProvider`, wired at `packages/happy-cli/src/daemon/run.ts:210-242`. A `LanDaemonProvider` slots in here. NOTE: the provider only abstracts tunnel *setup/URL advertising*; it does NOT change the listener auth model — that change lives in happy-server.
- **happy-server auth mode:** `CreateAppConfig.auth` ('tunnel' | 'loopback') + `assertOperatorIdentityGate` + dual-listener route mounting (`api.ts:104-117`). A new `auth: 'lan'` mode is the extension point (permit non-loopback bind ONLY when a per-request device verifier is active).
- **Codex opt-in gate:** `Feature::RemoteSession` (`codex/external/repos/codex-patched/codex-rs/features/src/lib.rs:171`, `// SANDBOX PATCH`). Per fork convention, gate the LAN variant via the Feature enum (default off), not an ad-hoc bool. (Codex-happy itself is loopback-only same-machine, so its connection code is largely unaffected; the surface is the `/remote on` opt-in + feature gate.)

## Candidate directions

### D-001: Additive opt-in LAN listener gated by a NEW fail-closed server-side per-device cryptographic auth mode  [RECOMMENDED]
- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: directly answers the operator's ask. The pluggable `DaemonTunnelProvider` seam + a new happy-server `auth: 'lan'` mode + the codex `Feature` gate let Dev Tunnels stay the unchanged default while LAN is an opt-in alternative. The auth gate reuses the EXISTING Ed25519/X25519 TOFU pairing key material (`packages/happy-app/sources/auth/pairing.ts`, the daemon's `tofuPublicKeys`): each blessed device proves possession of a pinned key on every session-plane request (and on the Socket.IO handshake), so the allowlist is enforced cryptographically at the listener, fail-closed. Enforcement-mechanism sub-options, strongest first: (i) **per-device public-key signed-request auth** (codex's recommended; reuses TOFU material; HTTP-over-LAN acceptable because the signature, not TLS, is the trust root) ; (ii) **mTLS with QR-pinned per-device client certs** (devils-advocate's "only airtight" framing; strongest but adds TLS termination + RN client-cert UX on the BOOX) ; (iii) per-device HMAC with nonce/timestamp replay protection (codex's lower-scope variant). Discovery (QR/manual LAN URL first; mDNS as a NON-security convenience only).
- Risks / friction: XL change surface spanning happy-server (`index.ts`, `api.ts`, `socket.ts`, `pairRoutes.ts`, new `lanDeviceAuth.ts`), happy-cli (`lanDaemonProvider.ts`, `dualListenerBinding.ts`, `run.ts`, `persistence.ts`), happy-app (`sync/tunnelProvider.ts`, `socketOptions.ts`, `auth/*`, a Settings toggle), and the codex Feature gate + `/remote on` surface. A subtly-wrong cert/signature check is a WORSE open door than Dev Tunnels because it looks secure. e-ink UX: QR/manual-IP pairing + DHCP IP churn breaking the pin. Fork-only; not cleanly upstreamable (happy-server `assertOperatorIdentityGate` is fork-local Sprint-A code).
- Cheapest validation: prototype ONE protected LAN route (e.g. a guarded `/v2/me/*` or a session route) that requires a pinned-device signature, bound to a LAN interface only when explicitly enabled, and exercise it from the BOOX over Wi-Fi with Dev Tunnels disabled — plus a HOSTILE-client test from a second laptop on the same LAN proving an unpaired/unsigned client gets fail-closed rejected on `/pair/complete` and every session route.
- Disconfirming observation: if Socket.IO handshakes, `/files/*`, `/pair/complete`, and every tunnel-only HTTP route cannot ALL be covered by one fail-closed device verifier without an auth-plane gap, the direction is unsafe as specified. Also disconfirmed if the corp Wi-Fi uses AP/client isolation or blocks inbound LAN ports (then no same-LAN transport is physically reachable — see D-003's probe).

### D-002: Challenge the premise — reuse a policy-permitted OUTBOUND tunnel the operator already runs (Cloudflare provider-swap)  [CONFIRM-OR-REJECT FIRST]
- Contributing lenses: [devils-advocate] (supported by copilot's "is the requirement no-Microsoft or no-cloud-at-all?" question)
- Why this might work: the operator ALREADY operates `happy.evyatar.dev` = a named **Cloudflare Tunnel** on this dev box, reachable from the tablet (fork AGENTS.md; `docs/fork-notes.md`). `cloudflared` is OUTBOUND-only (no inbound LAN port, no 0.0.0.0 bind), so it PRESERVES the exact gateway-as-identity-gate invariant `assertOperatorIdentityGate` depends on — happy-server keeps binding 127.0.0.1, the tunnel stays the access boundary, and NOTHING about the auth model changes. The only work is a `CloudflareTunnelDaemonProvider` on the same `DaemonTunnelProvider` seam. Cloudflare Access / a per-device service-token can even ADD edge-enforced per-device auth for free. On every axis except "works with zero internet," this dominates a bespoke LAN listener.
- Risks / friction: directly conflicts with the operator's stated motivation "WITHOUT routing through Microsoft/**cloud**" — Cloudflare IS cloud. If "no cloud at all" is a hard requirement (privacy/policy), this is out. Also latent risk: a generic "no third-party tunneling" DLP rule could eventually block Cloudflare too (though the operator's instance demonstrably works today).
- Cheapest validation: ONE operator question — "Does the tablet currently load `happy.evyatar.dev` over the corporate network, and is 'no cloud at all' a hard requirement?" A 5-minute answer can make the entire LAN effort unnecessary, OR firmly confirm LAN is the only path.
- Disconfirming observation: operator confirms "no cloud at all" is mandatory (privacy/air-gap/policy), OR the corp network also blocks all cloudflared egress. Then D-002 is dead and D-001 is the path.

### D-003: External cryptographic mesh (raw WireGuard) as the known-device boundary
- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: reframes "known devices on the same network" as "known devices on the same WireGuard mesh" — device identity = a pinned WG public key, enforced by the kernel before a packet reaches the listener; happy-server stays bound to a loopback-equivalent mesh interface, so the existing auth model is largely preserved (no new server auth mode). Pure-WireGuard (no coordination server) avoids any cloud dependency.
- Risks / friction: all three lenses flag the SAME dominant risk — Tailscale/Headscale's coordination/DERP plane is likely caught by the SAME policy that blocks Dev Tunnels (DOA), and many corp networks block UDP/51820 or use AP/client-isolation Wi-Fi where peers can't reach each other. Heavy WG key setup on a slow e-ink BOOX (Android cert/VPN profile UX). Still needs a non-loopback-bind carve-out for the mesh interface.
- Cheapest validation: on the ACTUAL corp Wi-Fi the tablet uses, bring up a single raw WireGuard tunnel (or even a raw TCP listen+connect) between dev box and tablet. If the handshake fails (UDP blocked / client isolation), EVERY same-LAN direction dies for the same reason — a decisive NO-GO probe for the whole LAN premise.
- Disconfirming observation: WG handshake / raw peer-to-peer connection fails on the corp Wi-Fi → the physical LAN path itself is non-viable, independent of mechanism.

## Recommendation & feasibility
**Recommended direction: D-001** (additive opt-in LAN listener with a new fail-closed, server-side, per-device cryptographic auth mode), because it is the operator's explicit ask and all three lenses agree it is feasible AND safe *only* with that auth floor. **Feasibility: GO — conditioned on two gates:**
1. **Security floor (hard):** the LAN listener MUST NOT bind non-loopback until a per-request cryptographic device verifier (signed-request reusing TOFU keys, or mTLS) covers `/pair/complete`, every tunnel-only HTTP route, and the Socket.IO handshake, fail-closed. IP/host/mDNS allowlists are explicitly insufficient.
2. **Premise check (cheap, do FIRST):** resolve D-002 with the operator — if the tablet already reaches `happy.evyatar.dev` and "no cloud at all" is NOT mandatory, a Cloudflare provider-swap is dramatically cheaper and preserves the security model. If "no cloud" is mandatory (the operator's stated lean), proceed with D-001.
3. **Physical-reachability probe:** before committing to LAN, run D-003's cheapest validation (raw peer-to-peer connection on the actual corp Wi-Fi) — if AP/client-isolation or inbound filtering blocks it, LAN is a NO-GO regardless of auth design.

## Open questions to carry into planning
- Concurrency: should LAN run as a THIRD listener alongside the live Dev Tunnels listener, or is a user-selected single remote listener acceptable (Dev Tunnels default, LAN opt-in per daemon start)?
- Enforcement mechanism choice: public-key signed-request (reuse Ed25519/X25519 TOFU) vs mTLS client certs vs HMAC+nonce — which best balances airtight-ness against BOOX/React-Native feasibility?
- Discovery: QR/manual LAN URL (reachability only) first, mDNS later as non-security convenience — acceptable on e-ink? How is DHCP IP churn / re-pinning handled?
- Where does the operator see and REVOKE known LAN devices (a device allowlist UI)?
- Does relaxing the fork's "never expose on 0.0.0.0/LAN/tunnels" invariant need a formal sign-off + `docs/security-model.md` update?
