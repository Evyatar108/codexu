# Brainstorm synthesis — ralph-overview snapshot freshness for the bookkeeper

**Idea:** Make the ralph-overview snapshot that agents read (via MCP `overview_parallel_ready_tasks` and `.ralph-overview/generated/snapshot.json`) reliably FRESH, so the bookkeeper never plans a batch from stale data. Observed 2026-06-06: the MCP returned 40 ready tasks, 28 already merged/archived, and omitted same-day filings — because the snapshot is only regenerated by a watcher/one-shot sync that was not running.

## Consensus framing

All three lenses independently reframed the problem the same way: **freshness alone is not the requirement — lifecycle correctness on every read is.** `data.json` is the durable, authoritative source for `tracked` / `merged` / `archived`; `snapshot.json` + job-state are only an *enrichment* layer for the heavier Ralph stage and dependency fields. The observed bug has two halves, and both trace to the MCP read path treating an eventually-consistent derived cache as authoritative for lifecycle gating:

- **False positives (28 merged/archived shown as ready):** `overview.parallel_ready_tasks` builds candidates from `snapshot.tasks` and filters via `isCandidateStage()`, which only checks Ralph `stage` against `EXCLUDED_STAGES = {shipped, replan-pending, blocked}` and **never checks `task.lifecycle`**. A stale snapshot carries stale lifecycle, and even a *fresh* snapshot can return a `lifecycle: merged` task if its derived Ralph stage is `planning`/`plan-ready`.
- **False negatives (same-day filings omitted):** a task filed in `data.json` after the last sync is simply absent from the stale snapshot, so it can never be surfaced.

Code grounding confirms the cheap fix is already 80% wired: `SnapshotReader.getOverviewData()` (snapshot-reader.ts) already reads `data.json` directly via `loadOverviewData()`; `parallel-ready-tasks.ts` already computes an advisory `snapshotStaleSince` (snapshot mtime vs data.json + job/group state) and a `watcherFailure` flag; and the MCP server already owns a `WatcherSupervisor`. The gap is purely that the **ready-task candidate construction does not use the authoritative lifecycle path.**

## Candidate directions

### D-001: Lifecycle-first sync-on-read + staleness guard
- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: It is the cheapest fix that addresses *both* halves of the observed bug. `SnapshotReader.getOverviewData()` already exists, so reading fresh `data.json` per call is a fast path (sub-second, not the ~17s full sync). Make `data.json` the authoritative spine for the task set + lifecycle inside `overview.parallel_ready_tasks`: read it fresh, exclude `lifecycle` `merged`/`archived` as a hard invariant (independent of Ralph stage), include newly-filed `tracked` tasks absent from the snapshot (using `initialStage` + `command.prompts`), and overlay snapshot Ralph stage / dependency data only as enrichment when present. Elevate the already-computed staleness signal into a returned `snapshotAgeMs` + clear stale reason. This is exactly the seed's "cheap staleness-warning now + lifecycle-only sync-on-read" layered combo.
- Risks / friction: Mixing fresh-lifecycle with possibly-older watcher-derived stage data in one response needs a clear contract so agents don't over-trust (or distrust) the secondary fields. New tasks absent from the snapshot have no derived dependency graph, so their readiness needs conservative semantics: direct `blockedOn`/lifecycle deps from `data.json` are authoritative, while PRD/story dependency readiness is marked unknown / awaiting-sync until the watcher catches up.
- Cheapest validation: Prototype the tool to read `data.json` mtime + lifecycle directly before filtering; return `snapshotAgeMs` + a `staleStageData` reason when `snapshot.json` is older than `data.json`; then re-run the 2026-06-06 stale scenario against the same files (mark many snapshot-ready tasks merged/archived, add a new tracked task, do NOT sync) and assert the merged/archived tasks disappear and the new task appears.
- Disconfirming observation: Wrong if a codexu-scale benchmark shows fresh `data.json` parse + data-first candidate construction is not comfortably sub-second, OR if the bookkeeper genuinely needs fully-current job-state/PRD dependency resolution before it can safely exclude merged/archived and include new filings. Concrete disproof: the data-first implementation still returns merged/archived tasks or omits the new task in the no-sync scenario.
- Version bump target: ralph-overview 2.9.0 → 2.10.0 (minor; additive MCP response fields + behavioral correctness fix).

### D-002: MCP-owned watcher as background accelerator (harden the existing WatcherSupervisor), not source of truth
- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: The MCP server already starts `WatcherSupervisor` + `SnapshotReader` on boot (index.ts) and coordinates an owner-heartbeat lease with passive/orphan modes. Hardening cold-start (the watcher's `start()` returns before its first full walk/write completes, leaving a ~17s window where the first call still sees old data) keeps the heavier stage/dependency fields fresher over a session.
- Risks / friction: Choosing this as the *primary* answer risks "solving yesterday's version" while missing the call-path lifecycle bug — a fresh snapshot still returns merged tasks. Long-lived watchers add coordination/cleanup risk across N concurrent agent sessions (lease contention, orphan reclamation brittle on Windows, chokidar depth caps are load-bearing for codexu's ~1.9M-file `.ralph` tree). A silently-dead MCP-owned watcher reintroduces staleness.
- Cheapest validation: Run `overview.watcher_status` on the installed plugin during the incident repro; if it shows an active same-repo watcher with no failure flag while `parallel_ready_tasks` still returns merged/archived tasks, watcher ownership is NOT the root cause (confirming D-001 is the real fix).
- Disconfirming observation: If multi-session tests show frequent lease contention / orphaned watchers / missed updates after restarts, making MCP own freshness adds another unreliable daemon instead of removing staleness.

### D-003: Snapshot freshness contract + sync-on-write hook (convenience layer only — insufficient alone)
- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: A post-edit hook after `data.json` writes is a nice latency optimization that keeps the snapshot warm after the common bookkeeping flow, and an explicit freshness contract on `snapshot.json` (mtime/age fields) helps direct snapshot consumers.
- Risks / friction: Sync-on-write is NOT a correctness boundary — it misses manual edits, git merges/cherry-picks, branch switches, failed hook installs, and any tool that doesn't participate in the hook. Relying on it alone creates false confidence. A pure staleness *guard* also fails alone: `parallel_ready_tasks` already computes `snapshotStaleSince` but still returns `readyTasks` from the stale snapshot, and agents can ignore warnings. Full sync-on-read (the heavy variant) is explicitly rejected: ~17s per call turns a quick planning tool into a blocking operation and invites timeouts / tool avoidance.
- Cheapest validation: Wrap the known `data.json` bookkeeping flow with a post-edit `sync` and measure whether `snapshot.json` updates immediately after a lifecycle flip without the watcher — then confirm it does nothing for a branch-switch / merge scenario.
- Disconfirming observation: If stale snapshots are commonly caused by branch switches / pulls / merges rather than the hooked write path, sync-on-write covers none of the real failure modes.

## Recommendation

**D-001 (layered combo)** is the clear cross-lens recommendation. It is the only direction that fixes both halves of the observed bug on every read regardless of watcher state, it reuses infrastructure that already exists (`getOverviewData()`, `snapshotStaleSince`, `watcherFailure`), and it matches the seed's stated "cheap staleness-warning now + lifecycle-only sync-on-read." D-002 is retained as a *background accelerator* for the secondary stage/dependency fields (no primary behavior change required; cold-start hardening is optional follow-up). D-003's sync-on-write is at most a convenience layer behind D-001's read-time lifecycle correctness; full sync-on-read is rejected on latency.

## Open questions to carry into planning
- When `data.json` is newer than `snapshot.json`, should `overview.parallel_ready_tasks` return lifecycle-correct results with a warning (lens-preferred), or fail closed unless an `allowStale` flag is passed?
- Should `overview.parallel_ready_tasks` EVER return a `lifecycle: merged`/`archived` task regardless of Ralph stage? (Recommend: no — make it a tested invariant with stale-snapshot fixtures.)
- For newly-filed tasks absent from the snapshot, what minimal readiness semantics are acceptable: `initialStage` + `command.prompts` only, `blockedOn` from `data.json`, or full PRD/dependencyGraph derivation?
- Should `snapshotAgeMs` / `snapshotStaleSince` be elevated from advisory metadata to a hard warning in the tool result prose so agents cannot silently plan from stale dynamic fields?
- (devils-advocate Q) Was the 2026-06-06 incident partly caused by codexu running an older marketplace build *without* the `WatcherSupervisor`, vs the call-path lifecycle gap? Even if both, the call-path gap is real and worth fixing.
