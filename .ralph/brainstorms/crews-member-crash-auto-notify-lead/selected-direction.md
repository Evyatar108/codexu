## Direction
D-001 (+ D-003 backstop) — Heartbeat-tick liveness monitor in the lead listener as the load-bearing core, with a lead turn-boundary hook sweep as the backstop + latch-reset home. Operator-selected 2026-06-07: hard-crash-only v1; D-002 dying-gasp is an optional fast-path, not v1-required.

## Goal
When a crew member dies a **high-confidence hard death** (`getMemberHealth` → `dead`: launcher pid gone, or no-pid + heartbeat stale past `HEARTBEAT_STALE_MS`), the crew **lead is pushed exactly one `review-required` `member-crashed` notification through the existing mailbox/armed-listener channel** — *including when the lead is sitting idle on an indefinitely-armed listener* (the failure mode that motivated the task: the 2026-06-06 silent brainstorm-member deaths and the ~9h-dark incident). No new lead-model poll loop; the lead never has to manually `list-members` to discover a dead member. Exactly one notification per dead member *incarnation* (generation-scoped dedupe), and **zero** notifications for `quiet`/`unknown`/healthy-idle members.

## Scope
### In Scope (v1)
- **D-001 — throttled heartbeat-tick liveness monitor in the lead listener (load-bearing core).** Piggyback a sweep on the lead listener's existing heartbeat `setInterval` (`lib/listener-loop.js:305-353`) — the ONLY periodic hook that fires during a quiet, indefinitely-armed (`timeoutMs === null`) idle wait. Throttle the sweep to a slow cadence (e.g. ≤ once / 60s, NOT every 10s heartbeat tick). On a high-confidence `alive|quiet|unknown → dead` transition for a member incarnation, synthesize a `member-crashed` system envelope and `appendSystemMailbox` it to the lead's own mailbox; deliver it in the same wake (append before the listener's own `consumeMailbox`/exit, or self-deliver) so the idle lead wakes promptly — do NOT leave it to sit until the next unrelated re-arm.
- **D-003 — lead turn-boundary hook sweep (backstop + latch-reset/hygiene home).** Run the same health-transition sweep at the lead's PreToolUse/Stop/SessionStart boundaries, where roster + state-cwd context is already natural, to cover the *actively-working* lead and as the durable home for latch-reset hygiene. (D-001 covers the idle-armed lead; D-003 covers the active lead and owns reset wiring.)
- **New `member-crashed` ENVELOPE kind** (NOT a turn-tag report kind). Add to `kindEnum` (`hooks/protocol/envelope.js:63-88`), to `DEFAULT_REVIEW_KINDS` (`hooks/protocol/review-required.js:1-12`) so it is review-required, and to the strict-ack auto-exempt set (`hooks/stop.js` `ACK_EXEMPT_KINDS`) so it is notification-only (the lead is not forced into an ack chore for a system notice) — i.e. **review-required AND strict-ack-exempt, modeled on `member-left`**. Add a `PAYLOAD_RULES` entry if it carries required fields.
- **Generation-scoped dedupe latch** keyed on `{ memberName, sessionId, launcherPid, launcherStartedAt, deadReason }`. Notify only when the current dead signature differs from the last-notified signature (NOT a boolean — a bare `crashNotified:true` either suppresses a valid re-crash after resume or needs brittle manual clearing).
- **Latch-reset wiring** into `repairManifestForResume` (`hooks/commands/resume-crew.js`) and clear-member cleanup, so a member that is resumed and later re-crashes notifies again.
- **High-confidence-only detection.** Reuse the existing `dead` classification; notify ONLY on `dead`, NEVER on `quiet`/`unknown`. Accept the documented false negatives (EPERM treated as alive, PID-recycling, wedged-launcher-as-`quiet`) — product copy must say "notify on high-confidence hard-dead transitions," not "notify when a member crashes."
- **Operator escalation may be a phase-2 config knob** (lead-only is the v1 default); not bundled into the core path. *(Borderline — keep the v1 path lead-only; only add the operator hook if it's a trivial gated dual-write.)*

### Out of Scope
- **Stalled / idle (9h-dark) detection** (`pidAlive && heartbeat-fresh && lastTurnAt frozen`, classified `alive`/`quiet`) — **DEFERRED to a separate `member-needs-attention` / auto-nudge follow-up task** (the lead is filing it). It is a distinct event with a longer threshold, an explicit healthy-idle carve-out (e.g. `listenerState==='armed' && queuedMailboxCount===0 && lastKind!=='progress'`), and a weaker default action (gentle auto-nudge, not a crash page). High false-positive risk: a member legitimately waiting on its armed listener is indistinguishable from a stall. **NOTE:** this means v1 (hard-crash-only) does NOT solve the 9h-dark class — that is an accepted, explicit limitation.
- **D-002 dying-gasp self-report** (member's own process best-effort emits a crash notice on unexpected exit) — OPTIONAL fast-path, NOT v1-required. It also misses `taskkill /T`, OS crash, power loss, and the UNKNOWN/-4094 lock-bug class that killed the 2026-06-06 members, so it can never replace the sweep; revisit as an enhancement.
- Operator always-on paging for every hard-dead member (would bypass lead triage / cause alert fatigue).

## Criteria
- A member transitioned to high-confidence `dead` while the lead is **idle on an indefinitely-armed listener** results in **exactly one** `member-crashed` `review-required` envelope delivered to the lead's mailbox that **wakes the armed listener**, within the throttled sweep cadence — verifiable with a synthetic dead-member fixture + an armed lead listener asserting a single delivery.
- A `quiet`, `unknown`, healthy-`alive`, or healthy-idle member produces **zero** `member-crashed` envelopes (no false positives on the non-`dead` states).
- Repeated sweeps over the same already-dead incarnation produce **no duplicate** notifications (generation-latch idempotency).
- After `/resume-crew` of a crashed member, a subsequent re-crash of the new incarnation produces a **fresh** notification (latch reset verified); `/clear-member` likewise clears the latch.
- `member-crashed` is review-required (surfaces in `/crews-review-mail`, bumps `lastReviewRequiredSeq`) but does NOT force a strict-ack (no ack chore) — modeled on `member-left`.
- D-003 turn-boundary sweep surfaces a dead member at the lead's next turn for the actively-working-lead case, idempotent across turns via the same latch.
- crews test suite green; version bumped via `scripts/bump-version.js`; the manifest exact-count test (`tests/protocol-manifest.test.js`) reconciled if a new top-level manifest field is added (or use a `manifest.custom.*` bag to avoid field-count churn).

## Context
- **The pivotal finding (verified in `lib/listener-loop.js`):** the seed's "sweep on the listener wake cycle (idle-timeout + every delivery)" is broken for quiet crashes. The lead listener is armed indefinitely — `timeoutMs === null` (`:127-134`), so the idle-timeout `bail()` is never installed (`:428`, `:440-442`); it delivers-then-exits (`:356-393`) only when *other* mail arrives. A hard crash writes no mail. The **only** periodic hook during a quiet idle wait is the heartbeat `setInterval` (~10s, `:305-353`) — hence D-001 lives there (throttled). This is honestly a *daemon-internal* monitor; that is distinct from the lead-MODEL polling the "always listeners, never poll" rule targets, and is the accepted carve-out.
- **The listener subprocess is single-actor today** (`:164-181`): it owns one mailbox + one listener epoch and imports a deliberately small config surface. D-001 adds cross-actor roster responsibility (`listNames` `hooks/actors.js:1144-1153` + `getMemberHealth` per member) + O(members) synchronous FS/`process.kill` reads per throttled tick — be mindful of Windows Defender/indexer lock pressure (the plugin has shipped many lock-hardening releases).
- **Ordering is load-bearing:** sweep-and-append BEFORE the listener's own `consumeMailbox` for the cycle (or self-deliver), else the crash row sits until the next re-arm — the delayed-delivery shape v3.12.0 just made observable.
- **Latch home is the main open question for planning:** the dead member's manifest (sweeper writes it under the member manifest lock — but races `repairManifestForResume`, which also takes that lock and rewrites `listenerState:'recoverable'`/`lastListenerPid:null`), vs a lead/crew-level `liveness-notifications.json`/incidents file (cleaner for multi-lead crews, but a new state file + lock discipline). Decide in planning. A new top-level manifest field churns `tests/protocol-manifest.test.js` (`manifestFields.length === 51`); a `manifest.custom.*` bag avoids that but is still protocol all writers/resetters must interpret consistently.
- **False-negative honesty (detection trust):** `isProcessAlive` treats EPERM as alive (`hooks/health.js:18-21`) and checks only pid existence (no image/parentage/start-time guard, unlike stop-member's recycle guards), so a recycled PID can mask a real death; a wedged launcher with a live pid + stale heartbeat is `quiet`, not `dead`. v1 deliberately fails toward *missed* notifications over spurious crash alarms.
- **Delivery seam (already exists):** `appendSystemMailbox` (`hooks/mailbox.js:541-582`) stamps `from.role='system'` + routes to the lead via the shared `appendMailboxWithSender` chokepoint, exactly as `member-joined`/`member-left`/`member-reply`/`proactive-report` already do. Detection seam (`hooks/health.js::getMemberHealth`, `deriveHealthState`, `HEARTBEAT_STALE_MS=5min`/`HEARTBEAT_ALIVE_MS=30s`) is reused as-is.
