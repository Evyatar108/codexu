# Brainstorm: ralph-orchestration-worktree-conditional-submodule-init

Three lenses ran at xhigh effort. Strong cross-lens convergence on the same first-cut direction and on the same alternative shapes; one unique Devil's-Advocate reframe questions whether the framing of the problem itself is correct. Synthesis preserves four candidate directions in scope-relevance order.

The currently-shipped behavior (worktree-create.mjs::runSubmoduleInit at line 259, invoked unconditionally from finishResult and the worktree-reuse path) was deliberately added in v5.42.0 with a cross-process lock and two env-var tunables — so any change needs to preserve that test gate (tests/test-submodule-worktree-init.sh) and the lock semantics, while shrinking the wall-clock cost on the spawns that don't actually need codex/ initialized.

---

### D-001: Phase-aware escape hatch (--no-submodule-init flag + plan-default-skip)

- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: Smallest viable change; ~1 day of dev work; ships immediate, measurable codexu wins on plan-phase spawns (which never need submodule code — they just write markdown) without touching impl-phase defaults at all. Adds a CLI flag `--no-submodule-init` to worktree-create.mjs (plus env var `RALPH_NO_SUBMODULE_INIT=1`), wires plan-with-ralph and decompose-plan plan-phase callers to pass it by default, and leaves convert-to-ralph-prd standalone Step 5 + decompose-plan Step 5b unchanged for impl members. Generalizes cleanly to non-codexu consumers: a no-op when the consumer repo has no submodules. Preserves init-all as the impl default, so the failure-mode "impl member silently fails to compile because submodule was skipped" is structurally impossible on impl paths. Produces telemetry for whether D-002 is worth the schema/detection investment.
- Risks / friction: Doesn't help impl spawns that don't touch submodules (explicit non-goal of this slice — codexu impl members would still pay the full submodule cost). Operator must remember to pass the flag manually for known-narrow impl scopes; if they forget, no impl wins. Plan worktrees that happen to grep into ai-developer-toolkit/ for context lookup would break with the new plan-default — codex specifically flagged this as the killing disconfirming case. Spawn-prompt authors and Ralph CLI callers both need updating in lockstep.
- Cheapest validation: Add `--no-submodule-init` + `RALPH_NO_SUBMODULE_INIT=1` to worktree-create.mjs (new flag, default off so behavior unchanged for unflagged callers), then wire plan-with-ralph and decompose-plan plan-worktree paths to pass it by default. Time 3 representative codexu plan spawns before/after; assert no plan-phase regressions in test-submodule-worktree-init.sh; eyeball wall-clock savings.
- Disconfirming observation: Within a week of shipping, either (a) plan/impl sessions forget the flag often enough that wall-clock waste remains roughly the same, OR (b) flag usage causes missing-submodule failures in normal plan flows because planners actually do need to read ai-developer-toolkit/ source during research/review phases. Either invalidates the "plan-default-skip is safe" claim.

### D-002: PRD-declared submodule policy with scoped init

- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: Converts inference into an explicit contract (Devil's Advocate's preferred framing — least dangerous form of optimization). Adds `submodulesNeeded: ["codex"]` (or `submoduleInit: { mode: "all|none|scoped|auto", paths: [...] }` per codex's schema question) to prd-schema.json. convert-to-ralph-prd auto-derives the field at PRD generation time by grepping plan.md and stories-outline.md against .gitmodules-declared paths; the operator can override or hand-edit. worktree-create.mjs reads the PRD field and initializes only the listed submodules. Covers the impl path that D-001 explicitly leaves alone. Makes intent visible to reviewers (the PRD becomes the audit trail for "this task does/doesn't need codex/").
- Risks / friction: Large effort (L per codex's estimate — schema + converter + decompose-plan + worktree-create + tests + copilot-mirror). Auto-derive from markdown grep is fragile — Devil's Advocate flagged multiple silent-failure scenarios: markdown grep misses generated paths, symlinked tools, renamed packages; PRD field goes stale after plan edits while reviewers assume the visible plan text is authoritative; a task edits only parent-repo orchestration code but its validation command invokes a script inside an uninitialized submodule (so the test runs against missing code and silently produces "0 tests found"). Existing PRDs without `submodulesNeeded` need a conservative fallback — Devil's Advocate and both other lenses agree this should be init-all by default to preserve current safety.
- Cheapest validation: Offline detector script — run the proposed auto-derive heuristic over 10 recent Ralph plans/PRDs from `.ralph/jobs/`, compare inferred `submodulesNeeded` against actual touched paths and verification commands. Reject the heuristic if it misses needed submodules in more than 1 of 10 OR if it marks 8+ of 10 as needing all submodules (eliminating the performance win).
- Disconfirming observation: The detector misses needed submodules in more than a rare edge case OR marks most tasks as needing all submodules. Either result means the "scoped init" performance win evaporates and the schema complexity buys nothing over D-001's coarser bypass.

### D-003: Lazy self-heal recovery as safety net for D-001 and/or D-002

- Contributing lenses: [codex, copilot, devils-advocate]
- Why this might work: Removes the "silent fail on missing submodule" failure mode that any detection-based policy creates. Two sub-patterns proposed across lenses: (codex) iteration-agent preflight runs `git submodule status` before any cargo/pnpm command and auto-inits if missing; (copilot) reactive recovery — when an impl command references a missing submodule path, init that specific submodule once + retry + log a clear recovery event. Could live in src/ralph.mjs as preflight, in story-doctor as escalation, or as prompt-guidance to the iteration agent. Cheap to add once one of D-001/D-002 ships; doesn't make sense as a standalone (without a primary, the unconditional init in worktree-create.mjs already covers it).
- Risks / friction: Detection of "this failure is missing-submodule vs a real compile/test failure" is non-trivial. Recovery may happen several minutes into an autonomous impl run, after the iteration agent has already made invalid assumptions (Devil's Advocate's silent-failure scenario: test command catches missing files, substitutes defaults, reports "0 tests found" — green-but-meaningless verification). Only empty submodule dirs are reliably detectable as "needs init"; partial/stale submodule checkouts are NOT detected and remain wrong. Adds prompt-template changes that must be mirrored across codex.md and copilot.md per the existing DURABLE-MEMORY parity rule.
- Cheapest validation: Prototype narrow recovery — pick one common command (`cargo check`), detect the "submodule directory empty" failure mode, init that one submodule, retry once, log a single-line "ralph-submodule-self-heal" event. Test against the codex/ submodule on a worktree where it was skipped via D-001.
- Disconfirming observation: Common missing-submodule failures aren't reliably classifiable separately from normal missing-file errors OR recovery commonly happens after the agent already produced a noisy failed iteration (defeating the "lazy is cheap" framing).

### D-004: Measure-first — validate the cost-driver before adding policy mechanism

- Contributing lenses: [devils-advocate]
- Why this might work: Before committing schema work + detection heuristic + override matrix + self-heal logic, run timing experiments to confirm the dominant cost driver. Devil's Advocate raises specific alternatives the team hasn't ruled out: lock contention (one batch waiting on another's init), recursive traversal of nested submodules, network cost vs checkout cost vs git-tree-walk cost, stale working-copy checks. If the dominant cost is lock contention, the fix is concurrency-tuning the lock; if it's the recursive-init walk, the fix is non-recursive init or selective submodule list; if it's the checkout phase, the fix could be shallow clone (`--depth 1`), partial clone (`--filter=blob:none`), or shared submodule object pool across worktrees on the same machine. Any of these could yield more value with less correctness risk than a detection-policy system.
- Risks / friction: Delays shipping any user-visible win by ~1-2 days of instrumentation + collection. If measurement confirms the obvious (unconditional-init IS the dominant cost), the team has burnt 1-2 days on data they already intuited. Doesn't help operators who want relief NOW. Single-lens direction — no codex/copilot endorsement, only Devil's Advocate.
- Cheapest validation: Instrument `runSubmoduleInit()` in worktree-create.mjs to emit one JSONL line per spawn to `~/.cache/ralph-orchestration/submodule-init-timing.jsonl` with fields { lock_wait_ms, git_walk_ms, checkout_ms, network_ms, total_ms, worktree, submodule_count }. Collect over ~1 week × ~50 spawns. Decide based on data whether D-001/D-002/D-003 or a different optimization is the right next step.
- Disconfirming observation: If measurement shows no-op `git submodule update` is reliably <1s on warm worktrees and lock-wait is rarely contested, then optimizing init-policy yields marginal wins and the original 3-min framing was a misdiagnosis (perhaps the first-time clone, not the steady-state init, is the actual cost). Conversely, if measurement confirms 3+ minutes of checkout-phase time on every spawn, the team can proceed to D-001 with confidence that the savings are real.

---

## Recommendation: D-001

D-001 ships the most learning per dev-day. Multi-lens consensus across codex + copilot + (partial) Devil's Advocate explicitly endorses staged rollout where the escape hatch lands FIRST. Codexu plan-phase spawns (which never need submodule code) get full ~3-min savings per spawn immediately. Risk surface is small: init-all stays the default for impl paths, non-codexu consumers see no behavior change (no-op flag), and the worst plausible regression (plan-phase needs ai-developer-toolkit/ source during research) is testable in a week of representative usage. Crucially, D-001 produces the data needed to decide whether D-002's schema complexity or D-003's self-heal logic is even worth building. If D-001 wins on plan-phase but doesn't move the needle on impl-phase, D-002 becomes the obvious next slice; if impl members rarely touch submodules anyway, D-002 may never need to ship.

The Devil's Advocate reframe in D-004 is worth keeping in scope as parallel work even while D-001 ships: instrumenting `runSubmoduleInit` to emit timing JSONL is cheap (~2 hours), runs alongside D-001 without blocking it, and answers whether the team should invest in D-002/D-003 OR pivot to a different optimization (shallow clone, partial clone, lock-tuning).

## Open questions carried forward

1. (codex) Should the canonical override be `--no-submodule-init` + `--init-submodules <list>` (two flags), or a single `--submodule-init=none|all|scoped` (one flag)? Both lenses raised this; pick one for the D-001 ship.
2. (codex + copilot) Should existing PRDs with no `submodulesNeeded` field retain current init-all behavior on resume, or auto-derive once at next worktree-create call and persist? Defaulting to init-all is safer; auto-derive+persist is more thorough.
3. (DA) For backward-compatible PRDs that don't declare submodule scope, is the safe default full init, no init with self-heal, or phase-dependent (plan=no-init, impl=full)? D-001 answers "phase-dependent" but D-002 forces a re-litigation.
4. (DA + codex) What exact signal tells an impl member a failure is missing-submodule-setup vs a real compile/test failure? Without this, D-003 self-heal is fragile.
5. (DA) Could the simpler fix capture most savings: skip submodule init only for plan worktrees, plus an explicit `--no-submodule-init` operator escape hatch, WITHOUT building D-002 detection? (This is essentially the D-001 ship plan.)
6. (codex) Where should recovery live if D-003 ships: src/ralph.mjs preflight, story-doctor escalation, or iteration-agent prompt guidance? Three different code surfaces with different observability properties.
7. (DA) How will reviewers detect green-but-meaningless verification (skipped tests, 0-test-discovery, fallback paths) caused by absent submodule content? Phase 5a code-reviewer prompt may need a check for this if D-001 or D-002 ships.
