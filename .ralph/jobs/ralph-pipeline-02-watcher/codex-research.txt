**Technical Constraints**

Several Plan 02 assumptions need tightening:

- `start()` cannot both “return immediately” and complete a cold-start full walk before watching unless it returns a handle with a `ready` promise. Prefer `async start(...) -> Promise<WatchHandle>`.
- The current plan double-runs cold start: CLI says run one-shot then call `start`, while watcher `start` also cold-starts. Pick one. Better: `start()` owns lock + cold-start + watcher setup; CLI `--watch` only calls `start`.
- Lock semantics are inconsistent. Plan says watcher releases lock only on stop, but verification says one-shot may acquire “between watcher ticks.” With lifetime watcher lock, one-shot should fail fast while watcher is running. This also aligns better with Plan 11 `sync.watch_status`.
- If Plan 11 needs `sync.watch_status`, Plan 02 should strongly consider writing JSON lock content now: `{ pid, process: 'standalone' | 'vite-plugin', startedAt }`, using `config.lockFile`.
- Incremental “one slug” updates are not safe if implemented as a naive `Map<slug, RalphPipelineState | null>`. Full sync has within-kind duplicate collapse and cross-kind precedence. If a winning job is deleted, a shadowed group/brainstorm may need promotion. Incremental logic must recompute the affected task’s candidate set or maintain a bundle cache and re-run the same collapse logic.
- File deletion behavior in the plan is too broad. Deleting `job-state.json` should not always remove the task; if `prd.json` remains, full sync would derive `plan-ready`. Only deleting the slug directory or all meaningful files should remove the entry.
- Tests should not be added to `ralphStage.test.ts` unless they only test stage derivation. Watcher tests deserve `tools/overview-viewer/src/__tests__/ralphWatcher.test.ts` or similar, under the node/SSR Vitest project.
- `tools/overview-viewer/vite.config.ts` is TypeScript and included in typecheck. Dynamic import of a root `.mjs` module may need a `.d.mts` declaration for `watch-ralph-state.mjs`.

**Implementation Suggestions**

Recommended plan refinements:

1. Add a shared sync helper in `scripts/sync-ralph-state.mjs` or `sync-core.mjs` so one-shot and watcher share `loadConfig`, `generatedFromCommit`, `walkRalphState`, unmatched logging, sidecar write, and lock acquisition.

2. In `sync-core.mjs`, refactor internals around reusable bundle assembly:
   - `readBundleForSlug({ kind, slug })`
   - `buildStateFromBundles(...)`
   - `deriveAffectedTaskUpdate(...)`
   
   This is safer than a simplistic `deriveOneSlug`, because it preserves duplicate resolution and `job > group > brainstorm`.

3. Make `watch-ralph-state.mjs` own:
   - `async start({ repoRoot, configPath?, debounceMs, processLabel, onWrite, onError })`
   - lock acquire/write metadata
   - cold-start full walk/write
   - `chokidar.watch(..., { ignoreInitial: true, awaitWriteFinish: ... })`
   - debounced changed-slug processing
   - `unlink` and `unlinkDir`
   - clean `stop()` that closes watcher, clears timers, unlinks only its own lock

4. Use config-derived watch roots and ignored globs. Keep the plan’s watched files as defaults, but map paths relative to `config.ralphRoot` and normalize Windows separators.

5. Update acceptance criteria to be directly verifiable:
   - CLI `--watch` performs exactly one cold-start write.
   - A fresh lock blocks a second watcher and one-shot sync.
   - Stale lock older than 60s is replaced with warning.
   - Malformed JSON keeps prior state in watcher mode and recovers after valid JSON.
   - Deleting only `job-state.json` rederives from remaining files; deleting the slug directory removes/promotes according to full-walk precedence.
   - Incremental tests include duplicate/cross-kind promotion.

6. Keep the downstream cascade requirement, but broaden it per the user request: after Phase 6 review converges, audit Plans 03-12 and `plans/ralph-pipeline-INDEX.md`, not only the hand-off list.
