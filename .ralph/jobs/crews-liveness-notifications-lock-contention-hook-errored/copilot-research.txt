### Technical Constraints

The latch lock only needs to serialize dedupe state, not the O(N) scan. Current code holds the lock across `getMemberHealth`, which on Windows may call CIM via `health.js::resolvePidAlive`, making lock duration scale with crew size and live-PID members.

Persist-after-append is load-bearing: mailbox append must happen before setting/writing the latch. If latch write fails, duplicate notifications are acceptable; lost notifications are not.

Moving the scan outside the latch does not materially weaken the six skip guards because the current latch never protects member manifests or health state anyway. For extra stale-candidate safety, re-read only candidate manifests under the short lock before append, but do not re-run the full crew scan there.

### Implementation Suggestions

Recommended primary plan: refactor `sweepMemberCrashNotifications` into two phases.

1. Scan outside the latch: build `candidates[]` containing `{ name, health, signature, detectedAt, message/payload }` after all six skip guards pass. This phase may do `listNames`, `readManifest`, `getMemberHealth`, and ownership checks without holding `liveness-notifications.json.lock`.

2. Lock briefly only for dedupe and writes: inside `withStateFileLock(getLatchPath(...))`, read latch, skip candidates whose signature is already latched, append `member-crashed`, then set latch signature and write latch. This preserves no-double-notify because concurrent sweeps serialize at dedupe time.

Keep all four call sites fail-soft exactly as-is and add an explicit regression test that forces `sweepMemberCrashNotifications` to throw/lock-timeout from `pre-tool-use.js` and asserts the hook allows the tool rather than returning a denial.

I would not raise the 2000ms timeout. After shrinking the lock window it should be sufficient; raising it would make hook hot paths block longer. Shared throttling between listener and turn-boundary sweepers is a reasonable secondary optimization, but it is not the root fix.
