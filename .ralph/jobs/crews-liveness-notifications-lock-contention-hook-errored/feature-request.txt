Plan a fix for the crews liveness-notifications crash-sweep lock contention that surfaces in .crews/logs/crews.log as repeated `member-crash-sweep-failed ... LockTimeoutError: timed out after 2000ms acquiring .crews/crews/<crew>/liveness-notifications.json.lock`.

THE BUG (operator-reported live 2026-06-24, confirmed from .crews/logs/crews.log): the lead-side crash-sweep (sweepMemberCrashNotifications in hooks/member-crash-notifications.js) repeatedly fails to acquire the per-crew `liveness-notifications.json.lock` within the DEFAULT 2000ms budget. On the ralph-pipeline crew (555 member directories on disk) the sweep holds the crew-wide latch lock for the ENTIRE duration of an O(N-members) crew scan (listNames + per-member readManifest + getMemberHealth, which on Windows calls CIM describeProcess for any live-PID launcher), far longer than 2000ms. Two lead-side sweepers run in DIFFERENT processes with INDEPENDENT throttles — the listener-loop heartbeat-tick sweep (D-001, in the armed-listener subprocess, in-process closure throttle) and the turn-boundary hook backstop (pre-tool-use / stop / session-start, file-stamp throttle) — so they collide on the long-held lock and the waiter times out.

IMPORTANT CORRECTION vs the original task framing (verified against source + the live log): the error ALREADY fails soft. All FOUR sweep call sites (pre-tool-use.js, stop.js, session-start.js, lib/listener-loop.js) wrap sweepMemberCrashNotifications in try/catch and only appendLog `member-crash-sweep-failed`; NO tool is denied and the lead is NOT a member-facing "hook errored" deny. The sweep is LEAD-ONLY (members never sweep), so the "5 concurrent members contend" framing is also incorrect — the contention is the single lead's OWN two sweeper processes racing on a lock held across a 555-member scan. The dead-holder lock-steal (v3.21.0 L3a) does NOT help here because the contending holder is ALIVE (the lead's other sweeper actively scanning).

The real symptoms are therefore: (a) recurring log noise (17+ `member-crash-sweep-failed` lines this session), and (b) a real member-crash notification can be DELAYED (not lost — the next successful sweep, the outbox, and listener re-arm still surface it).

THE CRITICAL INVARIANT (must be preserved and regression-tested): a crash-sweep lock failure must NEVER surface as a member-facing tool denial — the pre-tool-use (and stop / session-start / listener) sweep path must fail-soft (log, skip the sweep, ALLOW the tool). This is already true; the plan must HARDEN it with an explicit regression test, not regress it.

DESIGN GOALS — recommend ONE primary approach with tradeoffs, drawing on the v3.21.0 precedent (which layered multiple mitigations):
1. PRIMARY candidate — shrink the lock-hold window. The crew-wide latch lock is only needed to serialize the read-modify-write of the latch FILE (the per-crew dedup-signature map in liveness-notifications.json). The expensive part (listNames + readManifest + getMemberHealth/CIM per member) does NOT mutate the latch and does NOT need the lock. Restructure sweepMemberCrashNotifications so the crew scan + skip-guards + signature computation run OUTSIDE the latch lock, then take the lock briefly only to read latch -> per-candidate dedup-check -> appendSystemMailbox -> set+write latch. This collapses lock-hold from O(N members x CIM) to O(notify-count file write), so contention essentially disappears regardless of crew size. Preserve the persist-after-append correctness (latch written only after the mailbox append succeeds) and the no-double-notify guarantee (two concurrent sweeps serialize on the brief lock; the second's dedup-check sees the first's latch write).
2. Reduce contention frequency / coordinate the two sweepers — the listener-loop heartbeat-tick sweep (D-001) uses an in-process closure throttle; the hook backstop uses a file-stamp throttle (shouldThrottleTurnBoundarySweep). They are independent, so both can fire in the same ~60s window. Consider unifying them on the SHARED per-crew/per-lead file stamp so only ONE sweep actually runs per window crew-wide (debounce). Acceptable that this risks slightly delaying a real crash detection — the outbox + listener re-arm still surface the data.
3. Fail-soft single-attempt / no-retry-advisory on the latch lock — a failed acquire is a logged NO-OP that skips THIS cycle, never an error. (Already effectively true via try/catch; could be tightened to a short single-attempt so the hot path never blocks even briefly.)

Decide whether to combine the mandatory fail-soft hardening with (1) and/or (2), or some subset. Do NOT just raise the 2000ms timeout to 30s — that would make the pre-tool-use hot path BLOCK for up to 30s waiting on a lock held by a 555-member scan, which is worse than the current fail-soft-skip.
