### Codebase Architecture

This is a pnpm TypeScript monorepo with `happy-cli`, `happy-server`, and `@slopus/happy-wire` as the relevant packages. `happy-cli` owns daemon lifecycle, Dev Tunnels CLI calls, peer crypto, routing, and durable mailboxes. `happy-server` is embedded per daemon through `dualListenerBinding()` and exposes the tunnel-facing HTTP route. `happy-wire` owns shared Zod wire schemas.

### Technical Constraints

- Preserve `TunnelManager.listOperatorTunnels()` and `mintConnectToken()` behavior: Dev Tunnels management plane remains discovery/auth, with no phone/app/server relay.
- Backend must not inspect `X-Tunnel-Authorization`; Microsoft gateway consumes it.
- Current `peerTransport.ingestUrl()` picks `tunnel.tunnelUrl` or the first `portUri`, so a second ingest port requires port selection by `portNumber` or metadata, otherwise it may post to the wrong port.
- `TunnelManager.startHost()` already starts `devtunnel host <tunnelId>`, but lifecycle is minimal: detached process, error/exit logging, no readiness or multi-port modeling.
- `AgentCommsEnvelopeSchema.body` is `unknown`; sealed-body shape is currently enforced in `peerAuth.ts`, not shared wire.
- Cross-machine spawn approval is only a marker/helper today; there is no durable remote approval queue or UI/CLI approval path wired to execution.
- `mailbox.appendMessage()` validates `sessionId` and `sender` against a bare safe ID regex; remote sender passed today is `relayedEnvelope.from.sessionId`, not composite machine/session.

### Implementation Suggestions

Use the existing happy-cli seam as the integration point. First wire `controlServer`/router `deliverRemote` to a real `DevTunnelsPeerTransport`: resolve Scope A target machine to a reachable `PeerTransportTarget`, seal/sign the envelope with local TOFU keys and pinned peer ECDH key, then POST through Dev Tunnels.

For D-004, the cleanest compatible model is to make tunnel discovery port-aware before choosing co-located vs second port. If D-001 lands first, add an ingest-specific local port to machine state and ensure `devtunnel port create <tunnelId> --port-number <ingestPort> --protocol http`; `peerTransport` should choose the matching ingest `portNumber`. If D-001 has not landed, keep ingest co-located on the existing embedded happy-server tunnel port for the live-wiring task, but structure `PeerTransportTarget`/`OperatorTunnelPort` so switching to a second ingest port is a small follow-up.

Automate §8 with a two-daemon harness that avoids real Microsoft network dependency for normal CI by injecting `CommandRunner`, `ProcessSpawner`, and `FetchLike`, while still exercising real `signEnvelope`/`sealBody`/`verifyEnvelopeSignature`/`openSealedBody` and filesystem peer pins/mailboxes. Keep a manual real-devtunnel smoke as a separate opt-in test or script because it requires two logged-in machines.

For remote spawn, do not execute inside `/agent-comms/ingest` immediately. Append a durable approval request to the remote daemon/session first, require explicit operator approval, then call the existing `spawnSessionFromSession` path only after approval. This should reuse `requiresOperatorApproval()` and preserve the same signed/sealed envelope validation before any approval prompt is surfaced.
