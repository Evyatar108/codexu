## Architect Analysis

### Integration points

- `bin/ralph-overview.mjs`: 6-step resolver cascade, line 92 local-dev fallback is the only thing that changes.
- `.mcp.json`: stale — fix the AGENTS.md/file contradiction.
- `package.json:10-15`: `pnpm overview`, `pnpm sync-ralph-state`, `pnpm sync-ralph-state:watch` route through `bin/ralph-overview.mjs`. No direct toolkit-path references in package.json.
- `.crews/spawn-launchers/*.ps1`: cached-plugin paths only; auto-regenerated.
- Marketplace install paths (`~/.copilot/installed-plugins/`, `~/.claude/plugins/cache/`): independent of the submodule; remain marketplace-driven.

### Dependency graph

- codexu → ralph-overview plugin: overview data generation, watcher, MCP server, React viewer.
- codexu → crews plugin: member spawn / mailbox / stop workflow.
- codexu → ralph-orchestration: `/plan-with-ralph`, `/implement-with-ralph`, overview state, ship bookkeeping.
- **Submodule pinning is the right fit** for versioned source + editable dev checkout. Marketplace install remains the runtime source. Not npm dependency.

### Technical constraints

- **MAX_PATH risk** — codexu lives at `D:/harness-efforts/codexu/` already. Adding `ai-developer-toolkit/plugins/<plugin>/node_modules/...` deepens the path. The architect could not enumerate the deepest current path remotely; treat this as a known risk. Mitigation: assume some `node_modules` files will approach 260 chars; spot-check after first `pnpm install` in the submodule.
- **Two-commit flow** matches the existing codex submodule precedent:
  1. Edit in submodule, commit there.
  2. Update gitlink pointer in codexu, commit there.
- **Marketplace install coexistence**: no breakage from adding the submodule beside the cached install paths.

### Suggested implementation approach (architect's recommendation)

- Submodule-add + path rewrites in **one feature branch**, split into **2 commits**:
  1. `chore: add ai-developer-toolkit submodule` — `.gitmodules` + pointer.
  2. `chore: rewrite D:/ai-developer-toolkit paths to repo-relative` — file-category-grouped commits actually (per-category for traceability).
- Mid-flight test: `pnpm sync-ralph-state` and `pnpm overview` under both Claude Code and Copilot CLI; smoke-spawn a member.
- Submodule needs its own `pnpm install` workflow for plugin `node_modules`. Keep codexu's pnpm setup unchanged.

### Risk areas

- Drift between submodule pointer and marketplace install is **expected**: submodule = pinned dev source, marketplace install = live runtime. The bookkeeper docs must make this clear so operators don't get confused.
- Dev loop change: edit in-tree submodule → commit → push to gim-home → `copilot plugin update` to refresh the marketplace cache. Document the loop explicitly.
- Cross-machine: any operator pulling codexu post-merge needs `git submodule update --init`. Their old D:/ai-developer-toolkit sibling-checkout can stay as scratch.
- Rollback: revert the codexu commit(s); if submodule add landed, `git submodule deinit -f ai-developer-toolkit` cleans `.git/modules/` entry.

### Inconsistency noted

- AGENTS.md line 18 claims the old local-path `.mcp.json` entry "have been removed" — but `.mcp.json` still has it. Plan must resolve this contradiction.

## Codex Research

### Key new findings (not duplicated above)

- Codexu is `packageManager: pnpm@10.11.0` with workspaces under `packages/*`. Root `pnpm test` is currently a no-op via `vitest.config.ts`.
- CI is light: `.github/workflows/typecheck.yml` only watches `packages/happy-app/**`; `.github/workflows/cli-smoke-test.yml` only watches `packages/happy-cli/**`. Neither will run for `.gitmodules`, `AGENTS.md`, `.ralph-overview`, or submodule-pointer changes. **The CI invariant must be a new workflow or extended existing one with paths-trigger.**
- GitHub checkout for any script that reads the in-tree toolkit must use `submodules: true` (default is false).
- `bin/ralph-overview.mjs` checks for `.claude-plugin/plugin.json` + `node_modules/chokidar`. A freshly initialized submodule will not necessarily have plugin node_modules, so **the in-tree fallback is dev-mode-only, not a guaranteed production runtime** unless dependencies are installed.

### Version-check guidance

- Plugin versions are in `plugins/<plugin>/.claude-plugin/plugin.json`, **NOT in `plugins/<plugin>/package.json`** (the latter says `1.0.0` for ralph-overview, but `plugin.json` says `2.7.0`).
- Active plugin versions (researcher + codex consensus): ralph-overview 2.7.0, crews 3.0.0, ralph-orchestration 5.47.0.

### Implementation recommendations

- Make `bin/ralph-overview.mjs` fallback **script-relative** via `import.meta.url`, e.g., resolve `../ai-developer-toolkit/plugins/ralph-overview` from the script's location, NOT from process cwd. This works regardless of where the user `cd`s.
- Use `rg --hidden`, not plain `rg`, for any sweep — `.mcp.json`, `.agents`, `.ralph`, `.ralph-overview` are hidden paths.
- For invariant check: a Node script `tools/check-toolkit-submodule-invariants.mjs` + `package.json` script `check:toolkit-submodule`. Should verify `.gitmodules`, gitlink presence, plugin manifest versions, AND a scoped "Active versions" block in docs. **Avoid scanning every historical version mention** — CI will fail on intentional history/provenance text otherwise.
- Regenerate Ralph outputs with `pnpm sync-ralph-state` after `data.json` changes; verify with hidden grep excluding `ai-developer-toolkit/**` + explicit historical exclusions.
