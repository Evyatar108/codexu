**Technical Constraints**
The page must remain static HTML: no Vite/React, no sidecar JSON extraction, and no generator. That means the phase schema should be represented in existing HTML, most naturally as `data-task-phase`, `data-task-status`, and optional `data-*` attributes on each `<details class="cmd">`.

Current JS is class-driven, so `classifyCmd()`, `classifyAndOrderCmds()`, status filters, Today panel counts, and section counts must be updated together. If only CSS badges change, filters and counts will drift.

There is existing doc drift: `overview.html` marks `perf-WS3` and `1a-fork-doc` shipped, while `parallel-assignments.md` still says in progress. The migration plan should include a reconciliation pass rather than blindly converting table text.

`.ralph/jobs/devtunnels-E-cleanup/` is not present in this checkout, so treat it as optional context only. The three sibling plan docs exist but are untracked: `plans/task-phases.md`, `plans/overview-data-split.md`, and `plans/overview-vite-react.md`.

**Implementation Suggestions**
Use row-level attributes as the HTML-only schema:

`data-task-phase="plan-ready"` and `data-task-status="ok|blocked|paused"` on every command row, with optional attributes like `data-plan-only`, `data-plan-source`, `data-plan-source-ref`, `data-brainstorm-job-id`, `data-plan-job-id`, `data-implement-job-id`, `data-plan-review-iterations`, and `data-merge-commit`.

Keep the visual badge as a rendered/readable artifact: `.cmd-badge.b-plan-ready`, plus a smaller modifier pill only when status is `blocked` or `paused`. Leave legacy `.b-ready`, `.b-blocked`, `.b-paused`, `.b-closed`, `.b-inprogress` as aliases/fallbacks.

Update JS to classify phase separately from modifier. The status filter should probably become either “Phase” + “Modifier” filters, or keep current “Status” filter labels mapped onto derived buckets for backwards UX. For the PRD, specify this explicitly.

For kanban, preserve the three columns. Add phase pills to cards either manually or by adding `data-task-id` to cards and injecting from matching command rows; the current title-text matching at [plans/overview.html](D:/harness-efforts/codexu/plans/overview.html:3293) is useful but brittle.

For docs, add the enum convention to `parallel-assignments.md` preamble and expand the status table to `Phase | Modifier | Plan source/job | Commit` only if the PRD wants artifact visibility there; minimum requested scope is phase + status. Add one concise Standing rules paragraph to `codexu-roadmap.md`.

Verification should be static: grep every command row for `data-task-phase`, grep allowed enum values, open `overview.html` in dark/light mode, and manually flip one representative row through each progression path to ensure pills, filters, counts, and modifier rendering stay readable.
