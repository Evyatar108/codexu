I’m verifying the plan against the actual integration points and constraints in the repo.

### Feasibility

1. **[High]** The proposed `emitAgentTreeUpdate(sessionId, delta)` API does not match how routing works today. In `packages/happy-server\sources\app\events\eventRouter.ts:238-253` and `:369-397`, every routed event is keyed by **`userId` plus a recipient filter**; session rooms are named `user:${userId}:session:${sessionId}`. Step 8/9 and AC3 omit `userId`, so the proposed method signature and test shape cannot be implemented as described. The plan should either pass `userId` explicitly or reuse an existing `emitUpdate`/`emitEphemeral`-style signature.

2. **[Medium]** Step 3 points at `packages/happy-cli\src\codex\codexAppServerClient.ts:1701-1773`, but raw `item/*` normalization actually happens in `handleRawNotification()` at `:324-460`. That matters because `collabAgentToolCall` is a raw `item/*` shape, not a legacy `codex/event` notification. Implementing the feature in the location the plan cites would be working against the current parser structure.

### Completeness

1. **[High]** The server-side plan is missing an authorization check on the new inbound socket event. `sessionUpdateHandler()` is attached for **all** socket connections in `packages/happy-server\sources\app\api\socket.ts:226-230`, not just the daemon’s session-scoped CLI socket. If `agent-tree-update` only validates Zod shape and then fans out, any authenticated user-scoped socket could spoof agent-tree deltas into any session room. The handler needs to enforce `connection.connectionType === 'session-scoped'` and `connection.sessionId === data.sid` (or equivalent session-validity checks).

2. **[High]** AC1 is not runnable as written. The repo-root `package.json` has no `build` script, so `pnpm build` from `D:\harness-efforts\codexu` will fail immediately. The acceptance criterion needs to name the real command (`pnpm -r build` or the specific package builds).

3. **[High]** AC4 conflicts with the repo’s own test contract. `packages/happy-cli\agents.md` says the primary Codex acceptance file is `packages/happy-cli\src\codex\codex.integration.test.ts`, must use the **real** agent surface, and “mocked tests do not count as acceptance.” The plan’s fake-`CodexAppServerClient` scenario in that file is fine as a support check, but it is not a valid primary acceptance criterion under the existing rules.

4. **[Medium]** The documentation step is incomplete. `plans\codexu-roadmap.md:5-9` says changes that affect readiness/status must refresh `plans\overview.html` in the same commit. The plan updates the roadmap and recent-deliveries text but does not include `plans\overview.html`.
