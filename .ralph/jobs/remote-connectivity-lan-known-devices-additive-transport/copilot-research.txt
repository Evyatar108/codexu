### Technical Constraints

LAN must not reuse `auth: "tunnel"` unchanged: backend tunnel auth is intentionally empty because Dev Tunnels strips/verifies the gateway header. `assertOperatorIdentityGate()` currently rejects non-loopback for non-loopback auth unless `auth === "loopback"`; add a distinct `auth: "lan"` and require an active verifier before permitting non-loopback binds.

A LAN guard must cover `/pair/complete`, all tunnel-only REST routes, `/files/*` if local file serving is enabled, and Socket.IO handshakes. Pairing is especially sensitive because it can self-enroll today if exposed without Dev Tunnels.

### Implementation Suggestions

Add a shared `LanDeviceAuthVerifier` in happy-server and thread it through `CreateAppConfig`, `ConfigureApiOptions`, and `StartSocketOptions`. Use an `onRequest` hook for `auth === "lan"` so even `/pair/complete` is fail-closed; extend Socket.IO middleware with the same verifier.

Prefer signed-request auth over mTLS: React Native mTLS is high-friction. Use per-device Ed25519 keys, canonical request signing over method/path/body hash/timestamp/nonce, a short replay window, and a daemon-side known-device allowlist. Do not allow LAN self-enrollment; bless devices through an existing trusted path or local/QR operator action.

Implement `LanDaemonProvider` beside `DevTunnelsDaemonProvider`, extend daemon state with LAN endpoint metadata, and keep Dev Tunnels default behavior unchanged. In the app, make transport explicit in credentials (`dev-tunnels` vs `lan`) and route headers/socket options through transport-specific builders. Update `docs\security-model.md` and package AGENTS guidance to document the reviewed LAN exception.
