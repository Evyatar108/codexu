# Skill Suggestions

## Candidate: ralph-browser-verification-bridge
- Description: Detect Ralph stories whose acceptance criteria call for browser/HMR verification and route them through the available `agent-browser` skill instead of emitting a `Not-tested:` trailer.
- Triggers: Iteration agent is about to mark a story passed with browser/UI/HMR acceptance criteria; story carries a Phase 2.7 `tool-availability` warning naming dev-browser; an iteration is about to write a commit trailer like `Not-tested: Browser ... no browser automation tool available`.
- Target location: `plugins/ralph-orchestration/skills/browser-verification-bridge/SKILL.md`
- Evidence: Three consecutive `Not-tested:` trailers in the job git log — `11b1df70` (US-006 HMR), `256acbb3` (US-007 sidebar), `9e1c82b3` (US-008 tooltip). Three matching Phase 2.7 `criteriaWarnings` recorded in `notepad.md:37` (US-006:AC-015, US-007:AC-013, US-008:AC-012). `progress.txt:104,131,146` repeatedly record `Browser verification: SKIPPED ... no browser automation/dev-browser tool is available`, even though the `agent-browser` skill is listed as available in this environment.
- Rationale: The pattern shows agents inside Ralph iteration sub-sessions are not discovering the existing `agent-browser` skill and are skipping verification by default. A small bridge skill (or a Phase 2.7 enrichment) that names `agent-browser` explicitly when criteria mention browser/HMR/click/tooltip would convert three `Not-tested:` trailers per UI plan into actual verification. This is a discoverability/workflow gap, not a missing capability, so the candidate is a thin routing skill rather than new automation.

## Candidate: ralph-evidence-kind-normalizer
- Description: Map free-form `evidenceKind` values produced by iteration agents (`file-verified`, `test-pass`, `typecheck-pass`, `inspection`, etc.) onto the closed v5.25.0 manifest-verifier enum (`passed`, `skipped`, `manual-skip`, `fallback`, `absent-verified`) before structural validation runs.
- Triggers: An `analyze-iteration` Step 0.5 run logs `Manifest verifier ... advisory-skipped ... evidenceKind values do not match the closed enum`; an `iteration-result-*.json` contains an evidenceKind outside the closed enum.
- Target location: `plugins/ralph-orchestration/skills/evidence-kind-normalizer/SKILL.md`
- Evidence: `progress.txt:63` records `Manifest verifier (Step 0.5) advisory-skipped on all 3 iterations: iteration-result-*.json evidenceKind values (e.g., file-verified, test-pass, typecheck-pass, inspection) do not match the closed enum (passed, skipped, manual-skip, fallback, absent-verified); structural validation fails. Non-blocking.` Same advisory repeated in `notepad.md:39` for iterations 1-3. The contrast at `progress.txt:118` shows that once verifier-pass-fail-{4,5,6}.json were written with the canonical enum, all verdicts became `agree`.
- Rationale: Two consecutive batches in a single job hit the same closed-enum mismatch silently (non-blocking but corrosive to verifier signal). A normalizer skill with the explicit value table — invoked either inline in the iteration agent or as a Step 0.5 pre-pass in analyze-iteration — would restore manifest-verifier coverage without rewriting the verifier. The mapping rules are already implicit in iterations 4-6 of this job, so the skill body would mostly be the table + invocation contract.

## Candidate: ralph-cascade-terminal-evidence
- Description: When a cascade story needs to confirm an upstream plan is terminal, walk a documented fallback chain (`progress.json` -> `orchestrator-terminal.json` -> `job-state.json`) and emit the chosen evidence file path into the commit body so reviewers can audit the decision.
- Triggers: A story's acceptance criteria mention "cascade refresh", "upstream plan terminal", or a downstream-plan INDEX edit; `progress.json` is absent in the referenced upstream job directory.
- Target location: `plugins/ralph-orchestration/skills/cascade-terminal-evidence/SKILL.md`
- Evidence: `progress.txt:6` codifies the fallback under Codebase Patterns: `Cascade terminal checks may need job-state.json / orchestrator-terminal.json fallback evidence when an older Ralph job lacks progress.json; record the missing progress.json explicitly.` `progress.txt:159-164` shows the US-009 iteration applying that exact fallback (`Verified Plan 06 was terminal via orchestrator-terminal.json and job-state.json; progress.json was absent`). Commit `72c002c0` carries the `Constraint: Plan 06 terminal markers allowed direct cascade.` trailer, evidencing the procedural rule is already being threaded into commit metadata.
- Rationale: This fallback rule appears twice in one job (pattern + US-009 application) and is the kind of small but easy-to-skip procedural check that costs cascade correctness across parallel job groups. A 1-page skill listing the file precedence, the parallel-mode deferral interaction (`notepad.md:23-24`), and the required commit-trailer evidence would make the rule portable to every future cascade story rather than living only in `progress.txt` Codebase Patterns.
