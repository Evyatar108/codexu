# Skill Suggestions

## Candidate: verify-markdown-skill-body
- Description: Verify a SKILL.md (or other instruction-only markdown) by grepping for a checklist of required clauses/phrases, treating the markdown as instructions rather than executable code.
- Triggers: Implementing or modifying a repo-local SKILL.md whose "behavior" is markdown prose; acceptance criteria that say "manual smoke" or otherwise have no unit-testable surface; iteration agents that need a deterministic, fast pass/fail signal for markdown-only stories.
- Target location: plugins/ralph-orchestration/skills/verify-markdown-skill-body/SKILL.md (cross-job reusable; current evidence is inside Ralph stories)
- Evidence: progress.txt lines 60-67 (US-004 verified via "deterministic grep checks, including snapshot.recommendations, no recommendations available, --limit, --filter stage=") and lines 75-78 (US-005 "deterministic grep checks, including reviewOpenCount, deferredQuestionsCount, open Medium+, /implement-with-ralph resume, /work-on"); notepad.md lines 16 (Criteria Validator note "transitively covered by US-001/US-002 tests (CLI output) plus grep-based body assertions; skills are markdown, not unit-testable in vitest"); progress.txt line 67 lesson "Grep evidence for patterns beginning with `--` should use `grep -q -- '<pattern>'` so GNU grep does not parse the pattern as an option".
- Rationale: This pattern recurred for three stories in a single job, generated a non-obvious GNU-grep gotcha (`grep -q -- '<pattern>'` for `--`-prefixed needles) worth memorializing, and is reusable for any future markdown-only skill story across Ralph pipelines. A skill capturing the standard verification recipe (list required clauses up front, `grep -F -q` for literal phrases, `grep -q --` for option-like phrases, exit nonzero on first miss) would replace ad-hoc per-iteration grep design.

## Candidate: parallel-job-cascade-deferral
- Description: Before touching shared documentation/plan artifacts during a "cascade refresh" story, check whether peer parallel-pipeline jobs are still RUNNING; if so, defer the edits by appending dated entries to `notepad.md` under `## Deferred Cascade` and produce an empty commit recording the guard.
- Triggers: Stories that must update shared cross-plan documents (e.g. INDEX, sibling plan files) while peer Ralph jobs may concurrently edit the same files; review findings classified `wont_fix` due to peer job in flight; any story whose acceptance criteria reference "cascade", "shared plan docs", or "INDEX refresh".
- Target location: plugins/ralph-orchestration/skills/parallel-job-cascade-deferral/SKILL.md
- Evidence: prd.json US-006 (cascade refresh story); progress.txt lines 87-95 (US-006 iteration showed Plan 07 RUNNING, deferred via notepad ## Deferred Cascade, created empty commit `dd907aa`); notepad.md lines 18-25 (five concrete deferred entries naming peer job and downstream INDEX/Plan 07/08/09 audits); docs-review-findings.json F-004 (`status: wont_fix`, resolution: "Deferred to notepad.md ## Deferred Cascade per v5.40.0 parallel-safety rules; Plan 07 context-worker still RUNNING"); git commit `dd907aa911` trailer `Constraint: Plan 07 worker was RUNNING, so shared plan docs were not touched`.
- Rationale: This is a recurring v5.40.0+ parallel-safety pattern that already shows up in both the cascade story body and a docs-review wont_fix resolution, with a precise mechanical recipe (check `job-state.json.status`, write `## Deferred Cascade` rows with peer-job path/timestamp, empty commit with `Constraint:` trailer). Without a skill, every cascade story re-derives the guard. No existing ralph-orchestration skill encodes the peer-RUNNING check or the deferred-cascade notepad protocol.

## Candidate: skill-via-cli-helper
- Description: Author a repo-local skill so its SKILL.md is pure instructions that shell out to a thin Node CLI wrapper (resolving `repoRoot` via `git rev-parse --show-toplevel`, parsing flags, printing one JSON line to stdout) instead of duplicating predicate logic in markdown.
- Triggers: Drafting a new repo-local skill that needs to consume a shared ESM module (browser-safe predicate, plan snapshot reader, etc.); review findings that flag "inline `node -e`" or "duplicated stage table in markdown"; stories whose acceptance criteria mention both a skill body and a predicate/CLI module.
- Evidence: progress.txt lines 6-8 (codebase patterns "Plan 06 skills should shell out through scripts/lib/derive-next-command-cli.mjs instead of reimplementing snapshot reads or JSON quoting in markdown bodies" and "When a skill lets users match tasks by slug aliases, call derive-next-command-cli.mjs with the resolved canonical task.id"); progress.txt line 51 lesson "Keep the skill body as instructions that call the CLI helper; do not duplicate the stage predicate in markdown"; docs-review-findings.json F-003 (medium docs finding fixed by adding CLI wrapper to plan; resolution "Added CLI wrapper to Files+test+step 5+common mistake #3"); git commit `50b78f4b` trailer `Constraint: Skill body must shell out through derive-next-command-cli.mjs`; git commit `92411fcd` (docs F-003 fix documenting CLI wrapper as integration shape).
- Target location: plugins/ralph-orchestration/skills/skill-via-cli-helper/SKILL.md
- Rationale: Both an explicit codebase-pattern entry and a docs-review finding called this out, and the trailer history shows it was an enforced constraint across multiple stories. Plan 09 (MCP) and any future skill that consumes a shared module would benefit from the same recipe (CLI wrapper + JSON-line stdout + skill markdown that parses stdout). No existing skill in ralph-orchestration or the repo `.claude/skills` directory documents this integration shape.
