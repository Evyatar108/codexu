**Codebase Architecture**

This is a pnpm monorepo with fork-owned packages plus two major submodules. The relevant split is:

- `codex/`: fork wrapper around the Rust Codex checkout at `codex/external/repos/codex-patched/codex-rs/`, plus fork-only overlay crates under `codex/codex-rs-overlay/`.
- `ai-developer-toolkit/plugins/crews/`: JavaScript crews plugin, mostly hook-driven, with tests under `tests/`.
- `packages/happy-cli/`: TypeScript prior art for durable mailbox wake handling, but not the raw Codex runtime being targeted.

Codex is a Rust workspace. Relevant crates are `core`, `protocol`, `features`, `rmcp-client`, `codex-mcp`, and `core-plugins`. Crews is plain Node/CommonJS JavaScript and currently has no package-level `package.json`.

**Technical Constraints**

No MCP protocol change is needed. Option A, `notifications/resources/updated`, is the correct semantic shape, but should include `resources/subscribe` plumbing rather than relying on unsolicited updates. Option B, `notifications/message`, is a lower-effort fallback because Codex already bridges logging notifications, but it loses mailbox-resource semantics.

The Codex consumer should be general, not crews-specific: gated by `Feature::McpServerNotifications`, MCP server name allowlist, notification kind, and ideally URI prefix such as `crews://mailbox/`. Generic MCP notifications must remain event-only.

Do not implement this by editing only `realtime_text_for_event`; notifications currently enter through `tx_event`, and the bridge needs a session-owned consumer/callback/channel with access to `input_queue` and `request_pending_work_wake()`.

Codex fork rules from `codex/CLAUDE.md:16-22`: prefer overlay/new files; every upstream-canonical edit needs `// SANDBOX PATCH:`, a `patch-surface.md` §14 invariant row, and §15 rebase note. Local verification should prefer `cargo check --workspace` and focused crate/invariant tests, not full `cargo test --workspace`.

Crews constraints: no package-level `package.json`; adding an MCP SDK requires an explicit dependency/packaging plan. Otherwise keep the server dependency-free or local to the plugin packaging model. Verification is `node --check <changed-js-file>` and `node tests/run.js`.

**Implementation Suggestions**

Recommend Option A for v1: model a per-actor mailbox resource and emit `notifications/resources/updated { uri }`. Use Option B only as a fallback if `resources/subscribe` plumbing is deferred.

Implementation order should be:

1. Codex: add the notification-to-queued-input primitive, gated and allowlisted; add resource subscribe support for the crews mailbox URI; cover with invariant tests proving non-matching servers/kinds do not inject input.
2. Crews: add a small MCP server and wire it through `.codex-plugin` MCP config; emit mailbox resource updates from the existing mailbox write chokepoints; add startup catch-up when `lastReviewRequiredSeq > lastReviewedSeq`.
3. Crews gates: only after bridge health is detectable, relax listener reachability for Codex members. Keep Claude/Copilot unchanged. Keep review-required and strict-ack gates unchanged.

V1 should target Codex members only. The Codex bridge can be role-neutral, but lead reachability has stricter semantics and today’s lead runtime is Copilot; enable Codex leads later with a dedicated smoke.

Acceptance tests should prove: wake does not call `markReviewed`; only `review-mail` advances `lastReviewedSeq`; startup catch-up queues one hint; matching MCP notifications queue next-turn input; active turns are not preempted; rollback is just disabling the crews MCP server entry/feature gate while listener gates remain available.
