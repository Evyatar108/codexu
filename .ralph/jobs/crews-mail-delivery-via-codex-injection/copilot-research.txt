### Technical Constraints

No MCP protocol change is needed. Codex already bridges standard MCP server notifications, but raw Codex lacks the final native consumer that converts an allowlisted notification into queued next-turn input.

For the producer shape, **Option A (`notifications/resources/updated`) is semantically best**, because it models “mailbox resource changed.” However, spec-native Option A needs `resources.subscribe` support and client-side subscription plumbing. **Option B (`notifications/message`) is smaller**, because Codex already forwards logging notifications and no subscribe flow is required, but it is semantically weaker and lacks a mailbox URI/read-after-notify contract.

Crews must preserve strict review semantics: wake notification is only a hint; `.crews` mailbox history and `review-mail`/`markReviewed` remain the only review cursor path.

Codex fork constraints are significant: prefer overlay/new-file placement; any unavoidable upstream-canonical seam must be tiny, marked `SANDBOX PATCH`, documented in `patch-surface.md`, and covered by an invariant/test.
