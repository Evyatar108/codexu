### Feasibility

[High] The plan’s crews MCP config path is likely wrong. Codex plugin manifests require paths to start with `./` and resolve relative to the plugin root (`core-plugins/src/manifest.rs`, `loader.rs`). Existing toolkit Codex plugins use `plugins\<name>\.mcp.codex.json` with `"mcpServers": "./.mcp.codex.json"`, not `plugins\crews\.codex-plugin\.mcp.codex.json`. As written, the file list risks creating a config that Codex never loads.

[High] The capability flag has no listed launch stamping site. `CREWS_CODEX_WAKE_BRIDGE=1` must be set by the codex member launcher, but the crews files list omits `hooks\actors.js`, where codex launcher env and `-c` flags are actually emitted. Without updating both `buildLauncherCommand` and `buildLauncherInvocation`, `Feature::McpServerNotifications` and the proof flag may never be active.

[High] The crews-side wake producer lacks an IPC/trigger design. `appendMailboxWithSender(...)` runs in hook/CLI subprocesses, while the Codex MCP server is a separate long-lived stdio process. The plan says “after a successful durable mailbox write, emit” but does not specify whether the MCP server watches mailbox files, consumes a side-channel queue, or is otherwise signaled. A separate process cannot send notifications on the already-connected MCP transport just because `mailbox.js` ran.

### Completeness

[High] Add version-bump files to the crews job. The plan mentions `CHANGELOG.md` but not the six required version stamps updated by `plugins\crews\scripts\bump-version.js` (`.claude-plugin`, `.github/plugin`, `.codex-plugin`, and three marketplace indexes) nor `tests\version.test.js`. Installed-path dogfood is an AC, and stale plugin versions are a known cache/update failure mode.

[Medium] The plan should state how the crews MCP server is implemented without new package assumptions. `plugins\crews` is JavaScript-only and has no package-level `package.json`; adding an MCP SDK dependency would be a packaging change. Either specify a dependency/package update or require a minimal stdio JSON-RPC implementation.

[Medium] Reuse the existing Codex MCP notification bridge. `codex\codex-rs-overlay\codex-mcp-notification-bridge` already converts rmcp `LoggingMessage` notifications into `EventMsg::McpServerNotification`; the plan’s “new overlay helper/crate” wording risks duplicate/crisscross ownership. The new work should likely add a consumer/route helper adjacent to the existing bridge, not create another bridge crate.
