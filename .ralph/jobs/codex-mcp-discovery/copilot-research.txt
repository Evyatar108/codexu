The main Codex entrypoint is `packages/happy-cli/src/codex/runCodex.ts`, which creates the Happy session, starts the Happy MCP bridge, connects `CodexAppServerClient`, resumes or starts a thread, and then loops over queued user messages.

### Technical Constraints

- `zod` is already available in `packages/happy-cli`; no dependency change is needed.
- The requested schema is feasible, but **per-entry validation matters**: a single `z.record(...).safeParse(...)` on the whole `mcpServers` object would reject all servers at once. The requirement says invalid entries must be skipped individually.
- `CodexAppServerClient` already preserves `mcpServers` across reconnects once a thread has been started/resumed, so you do **not** need to modify reconnect logic separately.
- `runCodex.test.ts` does **not** exist. The repo uses multiple sibling `runCodex.*.test.ts` files instead.
- The provided test command is Unix/Git-Bash-shaped (`tee /tmp/...`). On this repo’s Windows guidance, the safer package-local command is `pnpm --filter happy exec vitest run <paths>`.
- One subtle edge case is not spelled out in the plan: if project `.mcp.json` defines a server named `happy`, a naive merge could override the internal bridge. The bridge should stay reserved.

### Implementation Suggestions

The natural integration point is **right before** `const mcpServers = { happy: ... }` in `runCodex.ts`. Capture `const cwd = process.cwd()` once, load `<cwd>/.mcp.json`, validate it, then build the merged `mcpServers` object used by both the resume and start paths.

Recommended shape:

1. Add a small helper in `packages/happy-cli/src/codex/` (or local helper in `runCodex.ts`) to load project MCP config.
2. Read `<cwd>/.mcp.json`; silently ignore `ENOENT`.
3. Parse top-level JSON; on broken JSON, `logger.warn(...)` and return `{}`.
4. Validate top-level `{ mcpServers }`, then validate each entry individually with Zod.
5. Merge validated project servers with the internal `happy` bridge, keeping `happy` reserved.
6. Pass the merged object to both:
   - `resumeExistingThread(...)`
   - `client.startThread(...)`

For tests, reuse the existing `runCodex.*.test.ts` mock pattern. The requested three support tests are straightforward there. I would also add a fourth support test for “one invalid entry + one valid entry keeps the valid one,” because that behavior is required by the spec but not covered by the three listed cases.

Overall, the plan is technically sound and fits the existing architecture. The only real gaps are test placement/acceptance wording and the need to define reserved-name merge behavior for the `happy` MCP server.
