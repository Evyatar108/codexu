I’m tracing the existing session metadata flow across app, wire, and server so I can map the exact integration points.

**Recommended direction:** use the existing **metadata-only** path, not new DB columns. The current system already stores session metadata as an opaque encrypted JSON string and propagates it end-to-end; adding dedicated `parentSessionId` / `spawnedChildren` columns would require a Prisma migration plus duplicate projections for little benefit in this single-user embedded-server architecture.

### Codebase Architecture
- **Monorepo / tooling:** pnpm workspace, TypeScript, Vitest.
- **Mobile app:** `packages/happy-app/` — React Native + Expo. Sync logic lives in `sources/sync/`.
- **Server:** `packages/happy-server/` — Fastify + Prisma/Postgres. Session CRUD and socket updates live under `sources/app/`.
- **Shared wire:** `packages/happy-wire/` — Zod schemas for shared update/message envelopes.
- **CLI/daemon:** `packages/happy-cli/` — owns session creation, metadata writes, fork/spawn flows.

### Technical Constraints
- **Composite ids are app-local.** The app uses `${machineId}:${localSessionId}`; server/daemon RPCs use bare local ids. `ops.test.ts` already enforces stripping the composite prefix before `fork-into-worktree`.
- **Server metadata is opaque.** Because `Session.metadata` is just a string, metadata-only is cheap; DB columns are expensive and require a human migration.
- **Undefined vs empty matters.** The pitfall in the request is real: `spawnedChildren` must stay `undefined` when absent; don’t normalize old sessions to `[]`.
- **No full session MMKV persistence exists today.** `packages/happy-app/sources/sync/persistence.ts` persists drafts/modes/replay seqs, not the full `sessions` map. So the acceptance line mentioning “MMKV” is broader than the current architecture unless it only means app-side merge/local overlay behavior.

### Implementation Suggestions
1. **Prefer metadata-only.** Extend:
   - `packages/happy-cli/src/api/types.ts`
   - `packages/happy-app/sources/sync/storageTypes.ts`
2. **Normalize refs at the app sync boundary.**
   - `sync.ts:toCompositeSession(...)` is the best place to map local ids to composite ids for `metadata.parentSessionId` / `metadata.spawnedChildren`.
   - Reuse the same normalization in the `'update-session'` handler so live updates and refetches match.
3. **Add store helpers in `storage.ts`.**
   - `getSessionParent(sid)` should read the current session’s `metadata.parentSessionId`.
   - `getSessionChildren(sid)` should resolve `metadata.spawnedChildren` against `state.sessions`.
   - Keep them pure lookups; no list/UI changes yet.
4. **CLI write point should be post-creation/post-spawn, not only initial metadata creation.**
   - `createSessionMetadata.ts` can seed child `parentSessionId` only if the parent ref is already known.
   - Parent `spawnedChildren` needs the child session id, so the natural surface is a later `ApiSessionClient.updateMetadata(...)` CAS update.
5. **Tests to extend**
   - `packages/happy-app/sources/sync/storageTypes.spec.ts`
   - `packages/happy-app/sources/sync/storage.applySessions.spec.ts`
   - add helper-focused store tests for parent/child lookup
   - `packages/happy-app/sources/sync/sync.test.ts` for composite-id normalization on `update-session`
   - CLI tests where metadata types/writes are updated

**Bottom line:** the plan is feasible, and the natural implementation is **CLI metadata type + app metadata type + app sync normalization + store helpers**, while leaving happy-server/happy-wire structurally unchanged unless the operator explicitly wants queryable server-side parent/child columns.
