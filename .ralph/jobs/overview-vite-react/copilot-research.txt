### Technical Constraints

- **Update both workspace manifests**: `pnpm-workspace.yaml` and root `package.json`. The plan currently mentions only the former.
- **Do not rely on network loading**. Existing viewer and skill both assume `file://` compatibility and synchronous `window.OVERVIEW_DATA` availability.
- `plans/overview-data.js` lives **outside** the future package root, so Vite will need:
  - `server.fs.allow`
  - explicit watcher registration
- Existing UI state is persisted in localStorage:
  - `codexu-overview-details-state-v2`
  - `codexu-overview-last-visit-v1`
  - `codexu-overview-notes-v1`
- Current viewer injects **trusted HTML** in more places than just kanban/phase raw nodes:
  - `kanbanCards[].html`
  - `command.descriptionHtml`
  - `command.warnings[].html`
  - `phaseTree raw.html`
  - `phaseTree task-ref.trailingHtml`
- `renderPhaseTree()` currently derives class from **`task.phase` only**, not `task.status`; blocked/paused are not reflected there today.
- There is **no root ESLint config** for workspace packages, so any `react/no-danger` rule would need package-local setup or should be omitted.

### Implementation Suggestions

- Use `tools/overview-viewer/` as a real workspace package, but mirror existing repo conventions:
  - React/Vite dependency pattern from `packages/codium`
  - strict TS / `jsx: react-jsx` shape from `packages/happy-app`
- Treat the React port as a **data-driven rewrite**, not a DOM-effect wrapper around `applyEnrichments()`.
- Natural integration points:
  - `src/data/schema.ts` — based on **actual shipped data**, not only the plan prose
  - `useOverviewData()` — `useSyncExternalStore` over `window.OVERVIEW_DATA`
  - components for `TaskCommand`, `KanbanCard`, `StatusBadge`, `PhaseTree`, `RunsLog`, `TodayPanel`
  - hooks for URL filter, hash nav, and persistent expansion
- Preserve exact behavior first:
  - badge text/glyph map
  - `?tasks=` filter
  - hash expand/scroll to `#cmd-...`
  - current kanban ordering algorithm
  - current filter axes
  - current localStorage keys
- Define TS types defensively:
