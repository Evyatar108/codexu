**Technical Constraints**

- Windows x64 only. No Unix binary is built today.
- Existing upstream install script version regex only allows `x.y.z[-alpha|-beta]`; this fork needs to accept versions like `0.135.0-copilot-api.1`.
- There is no `codex install` subcommand. The installer must own PATH wiring.
- Windows file locking requires killing `codex` and `codex-core` before replacing executables.
- Directly running `codex.exe` bypasses the JS shim that adds `rg.exe` to child PATH. If using a custom `~/.codex-fork` layout, put `rg.exe` in the same PATH-visible directory or create a recognized standalone package layout.
- CI workflow exists, but manual `/publish-sandbox-patch` is currently the real release path because Actions are documented as blocked. The R2 upload must not live only in CI unless the operator unblocks Actions.
- R2 credentials are new infrastructure. No repo dependency on `wrangler` exists today.

**Implementation Suggestions**

Use a static R2 layout first, not a Worker:

```text
/latest
/manifest.json
/releases/<version>/codex-<version>-win32-x64.tgz
/releases/<version>/codex-<version>-win32-x64.tgz.sha256
/install.ps1
/install.sh
```

The natural code integration is a small wrapper-owned release helper invoked from both [publish-npm.yml](D:/harness-efforts/codexu/codex/.github/workflows/publish-npm.yml:254) and [publish-sandbox-patch.md](D:/harness-efforts/codexu/codex/.claude/commands/publish-sandbox-patch.md:292). It should take `version`, `bundle path`, `base URL`, and bucket config; compute SHA-256 and size; write `manifest.json` and `latest`; then upload all four release objects. This avoids duplicating manifest logic across CI and manual release docs.

For `install.ps1`, reuse patterns from upstream `install.ps1`: `Invoke-WithInstallLock`, `Path-Contains`, `Prepend-PathEntry`, staging-before-move, checksum verification, and user-scope PATH update. Add testability knobs like `CODEX_INSTALL_ROOT`, `CODEX_BASE_URL`, and `CODEX_NON_INTERACTIVE`.

Prefer staging extraction first, then atomic replace/retarget. That keeps AC-4 strong: a bad hash or malformed tarball cannot partially mutate the live install.

For layout, either:

1. Minimal AC layout: `~/.codex-fork/bin` contains `codex.exe`, `codex-core.exe`, `codex-windows-sandbox-setup.exe`, `codex-command-runner.exe`, and `rg.exe`; add only that dir to User PATH.
2. More compatible layout: adapt upstream standalone layout under `~/.codex/packages/standalone/releases/...` so `codex doctor`, update actions, and bundled resource detection already classify it as standalone.

I would choose option 2 unless the operator strongly wants the literal `~/.codex-fork` root. It reduces follow-up changes in doctor/update behavior.
