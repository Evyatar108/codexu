**Technical Constraints**
The sidecar must be `.js`, not `.json`, because the page is designed to work from `file://`; `fetch()` will break under Chromium file-origin rules.

Existing JS assumes command rows and cards already exist in the DOM before the IIFEs run. A data-driven renderer must execute before `renderPhaseBadges`, `injectTaskScopeChips`, counts, filters, spawn links, and run-history injection.

Preserve these DOM contracts:

- `id="cmd-${task.id}"` for hash links.
- `data-task-id`, `data-task-phase`, `data-task-status`, `data-task-scope`, `data-plan-only`, `data-merge-commit`.
- URL filter currently uses `?tasks=a,b`, not `?id=`.
- Scope values include `bookkeeping|codexu`, `codex|codexu`, `codex`, and `codexu`; schema should not narrow to only codex/codexu.
- Prompt bodies currently live in `<pre>` with HTML entities decoded by `textContent`; JS strings must preserve the decoded clipboard text.

The proposed single `kanbanColumn` field is too small if identical rendering is required. Current kanban has multiple cards per task with different titles/subtexts. Use `kanbanCards: []` per task or a top-level `kanbanCards` array.

**Implementation Suggestions**
Use `plans/overview-data.js` as the source of truth, but keep compatibility by re-emitting the same DOM shape first. Then most existing IIFEs can continue working with smaller changes.

Recommended data shape additions:

- `meta: { generatedAt, generatedFromCommit }`
- `tasks[]`
- `task.command: { summaryHtml, descriptionHtml, warnings[], planPrompt }`
- `task.kanbanCards[]` rather than one `kanbanColumn`
- `task.lastTouchedAt`, `effortHours`, `risk`, `workstream`, `sizeBucket`, `cadence`
- `runs`, `periodic`
- Optional `phaseTree` only if the phase tree is actually data-driven in this pass.

Render with DOM APIs and `textContent` where possible. For existing rich text like `<code>` and `<a>` in descriptions, either store trusted HTML fragments or use a small structured inline-token format; trusted fragments are simpler for this static local file.

Add `tools/overview/validate.mjs` and a root script such as `overview:validate`. Validate duplicate task ids, enums, scope labels, `blockedBy`/`spawnedFrom` refs, run `taskId` refs, kanban refs, and parity with the status table in `plans/parallel-assignments.md`.

The skill update is mandatory. The current skill still tells agents to edit `overview.html`, `data-task-phase`, and `roadmap-data`; that must move to “edit the task entry in `plans/overview-data.js`.”
