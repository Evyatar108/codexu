**Codebase Architecture**

This repo is a pnpm monorepo plus a Rust Codex submodule.

- `packages/happy-cli`: TypeScript CLI package, built with `tsc`, `pkgroll`, tested with Vitest. Codex mode starts at `src/commands/codexCommand.ts`, then `src/codex/runCodex.ts`, then `src/codex/codexAppServerClient.ts`.
- `packages/happy-wire`, `happy-server`, `happy-app`: shared protocol/server/app packages, mostly not central to this feature unless session protocol rendering changes.
- `codex/`: git submodule. Rust workspace lives under `codex/external/repos/codex-patched/codex-rs`, with wrapper/fork docs under `codex/docs/implementation`.
- Codex fork policy: upstream-canonical edits under `external/repos/codex-patched/codex-rs` need `// SANDBOX PATCH:` markers and `codex/docs/implementation/patch-surface.md` updates.

**Technical Constraints**

- The Codex feature flag is fresh-spawn configuration. `CodexAppServerClient.connect()` may reattach to an existing WS app-server, so changing a happy-cli setting will not affect already-running Codex daemons unless the app-server is restarted or discovery is bypassed.
- `extraAppServerArgs` already appends raw argv to both stdio and WS spawns. The happy setting can add `-c features.background_process_notification=true`, but precedence with user `--codex-arg` must be deliberate.
- `happy codex doctor` currently cannot prove whether a live app-server was spawned with this flag; discovery records do not store feature args. Either add a non-secret discovery/lifecycle field, or report “setting enabled, live daemon unknown/restart required.”
- Primary LOW-A should not use `MessageQueue2`; Codex core already starts the synthetic turn. The queue consumer pattern is only for LOW-B fallback.
- The turn-end seam should run only after `active_turn` is cleared in `on_task_finished()`. Placing it earlier risks preserving the active-turn race.
- Tool-description edits require updating exact expected strings in `shell_spec_tests.rs`.
- Codex verification should use `just fmt`, `cargo check --workspace`, and focused `just test -p codex-core`; avoid broad workspace tests locally unless needed.

**Implementation Suggestions**

Use LOW-A first.

1. In Codex, add a small feature-gated `maybe_start_turn_for_pending_work().await` in `core/src/tasks/mod.rs` after `cleared_active_turn` succeeds, ideally after the existing `GoalRuntimeEvent::MaybeContinueIfIdle` call. Mark with `// SANDBOX PATCH:` and update `codex/docs/implementation/patch-surface.md`.

2. Add a regression test in `core/src/unified_exec/process_manager_tests.rs`: set an active turn, spawn a background process with exit watcher, wait until the notification is queued but no turn starts, finish/clear the active turn through the relevant task path or a tight helper, then assert the queued notification drains into a synthetic turn.

3. In happy-cli, add a default-off setting in `persistence.ts`, e.g. `codexBackgroundProcessNotifications?: { enabled?: boolean }` or a simple boolean. In `runCodex.ts`, when enabled, append `['-c', 'features.background_process_notification=true']` into `codexAppServerArgs` before constructing `CodexAppServerClient`.

4. Add tests that setting off preserves argv exactly and setting on adds the `-c` flag for both stdio and WS spawn paths. Existing `extraAppServerArgs` tests in `codexAppServerClient.test.ts` are the right pattern.

5. Extend doctor/status carefully. Best option: add a sanitized discovery-record field written at spawn, then render “async background completion: enabled/disabled/unknown; restart required if setting and live daemon disagree.”

6. For model policy, prefer minimal wording changes in `shell_spec.rs`: tell the model to use short `yield_time_ms` and end the turn for fire-and-forget work, and to avoid `await_background_completion` or empty `write_stdin` polling when async completion is desired.

7. Live validation remains necessary: happy-cli’s event handler will likely render Codex-initiated `task_started` / `agent_message` / `task_complete` events, but `sendTurnAndWait()` only owns submitted turns, so readiness/push behavior for self-started turns should be verified explicitly.
