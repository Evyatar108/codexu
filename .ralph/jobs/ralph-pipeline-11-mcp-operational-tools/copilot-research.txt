### Technical Constraints

Stdout is reserved for MCP JSON-RPC traffic, so spawned child output must be piped/ring-buffered and never inherited. Diagnostics should stay on stderr.

Windows support matters: `child_process.spawn(cmd, args, { shell: true })` is appropriate for `pnpm` because Windows resolves `pnpm` via a `.cmd` shim. Normalize `\r\n` when buffering logs.

Async cleanup cannot reliably run from Node’s `exit` event. Use SIGINT/SIGTERM for awaited `stopAll()`. If an `exit` handler is added, it can only do best-effort synchronous cleanup.

The plan’s “modify `index.ts` to register tools” is inaccurate for this codebase; registration belongs in `server.ts`. `index.ts` should only own lifecycle wiring.

### Implementation Suggestions

Add `tools\overview-mcp\src\process-manager.ts` with injectable spawn factory for tests, per-stream 1000-line ring buffers, line splitting that handles chunk boundaries, an `AlreadyRunningError`, and `stopAll()`.

Extend `ServerContext` to include `processManager`, then implement thin tool modules under `tools\overview-mcp\src\tools\`. Use existing `toToolResult()` but return the operational shape directly, e.g. `{ ok: true, url, pid }`, not necessarily nested under `data`.

For `overview.sync.watch_status`, prefer exporting shared helpers from `scripts\lib\sync-lock.mjs` rather than duplicating stale/liveness behavior. At minimum, share the 60s stale threshold and mirror `process.kill(pid, 0)` handling exactly.
