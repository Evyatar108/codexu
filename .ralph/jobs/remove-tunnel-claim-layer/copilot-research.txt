**Technical constraints**

- The app guidance is explicit that **session/machine-scoped network calls must use the `apiSocket` scope builders**, but **WS1 does not need any `apiSocket` changes**. The natural edit point is still `refreshClaim.ts`.
- `parseTunnelClaimPayload(...)` returns fields as `unknown`, so the skip logic must explicitly guard `typeof payload.exp === 'number'`.
- `MIN_REFRESH_INTERVAL_MS` is already load-bearing throttling and should stay on the **network-refresh path**.
- `validateFreshClaim(...)` currently validates only freshly fetched claims. For the skip path, the safest pattern is: **only skip when the cached claim is clearly usable; otherwise fall through to existing refresh behavior**.
- Important hidden constraint: **fresh claims are not currently persisted back anywhere obvious**. `refreshTunnelClaim(...)` returns the new string, but `machineAuth.ts` does not write it back, and `sync.ts` often reuses in-memory credentials. That means a pure “check `credentials.tunnelClaim` and skip” change helps while the originally stored claim is still fresh, but may stop helping after the first true refresh unless the updated claim is also stored or mutated in-memory.
- There is apparent branch drift around tests: `refreshClaim.test.ts` still references the old `/pair/status` / `X-Tunnel-Connect` flow, while current implementation and server docs use `/pair/complete` and `X-Tunnel-Authorization` / `X-Codexu-Authorization`. A fresh agent should sanity-check that before assuming the baseline tests are already aligned.

**Implementation suggestions**

The natural integration point is **at the top of `refreshTunnelClaimOnce(...)` in `packages/happy-app/sources/sync/refreshClaim.ts`**:

1. Parse `credentials.tunnelClaim` with `parseTunnelClaimPayload(...)`.
2. Compute `nowS = Math.floor(Date.now() / 1000)`.
3. If `exp - nowS > SAFETY_WINDOW_S`, return the cached claim immediately.
4. Otherwise, continue the existing throttled `/pair/complete` refresh path unchanged.

A local constant like `SAFETY_WINDOW_S = 90` in `refreshClaim.ts` fits the existing style and is easy to test.

If the goal is the full steady-state perf win described in the plan, I’d also account for the persistence gap: after a successful network refresh, update the active cached claim (storage and/or live in-memory credentials) so future calls can benefit from the skip path beyond the very first hour after pairing.

For tests, the right new assertion is exactly the one the plan describes: construct a claim whose `exp` is comfortably ahead of `now + SAFETY_WINDOW_S`, call `refreshTunnelClaim(...)`, and assert it returns the cached claim with **no `fetch` call**.
